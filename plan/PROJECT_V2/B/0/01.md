# B/0/1 - Human discovery and dual-planner draft sessions

## Quick reference

| Campo | Valor |
|---|---|
| Stage | B - Advanced planning workflow |
| Branch | `feature/V2-B-0-1-dual-planner-drafts` |
| Depende de | B/0/0 |
| Esfuerzo | L (1-2d) |

## Por que existe?

La calidad del plan mejora si dos planners razonan de forma independiente antes
de converger. Pero esa fase solo es util si antes existe un brief humano real:
el orquestador debe conversar con el operador, preguntar aclaraciones, resumir
el alcance y obtener confirmacion de que ya puede lanzar planners. Para que sea
auditable y no headless, el Gateway debe crear dos sesiones de planner con
`agent.spawn` + `agent.ask`, asociadas al mismo `traceId`, y guardar cada draft
como artefacto.

## Que hay que hacer?

Implementar una utilidad/orquestacion de planning avanzado que primero ejecute
la fase `discover_with_human`, produzca un `planning_brief` auditado, y despues
lance dos planners con modelos distintos y persista sus drafts.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V2-B-0-1-dual-planner-drafts
```

### 2. Discovery humano interactivo

El flujo no debe empezar con planners vacios ni con un fixture opaco. El
workflow Gateway humano-facing, invocado por la herramienta MCP, debe mantener
una conversacion in-band con el operador hasta que el alcance este razonablemente
claro o el operador indique explicitamente "lanza planners".

El workflow debe registrar cada instruccion relevante como
`human_planning_note` y construir un `planning_brief` con:

- objetivo;
- no objetivos;
- restricciones;
- repos/rutas afectadas;
- decisiones ya tomadas;
- dudas abiertas.

El brief se guarda con `artifact.put(kind="planning_brief")` antes de crear los
planners. Si quedan dudas de alto nivel, el brief debe incluirlas y los planners
deben tratarlas como `OPEN DECISIONS / QUESTIONS FOR HUMAN`.

El brief incluye tambien campos normalizados que otras fases deben leer:

- `codexReviewRequired: boolean` - `true` solo si el humano exige
  explicitamente review Codex sin fallback;
- `planningId` - id estable usado para reconstruir iteraciones y notas.
- `discoveryCycle` - empieza en `1` para el primer brief sellado.

`autoApproveScopes` no vive en `planning_brief`: se guarda en estado de
orquestacion para `(traceId, planningId)`. El brief puede reflejar la decision
en texto para auditoria, pero el approval path lee siempre del estado de
orquestacion.

### 2.1 Criterio de fin de discovery

El orquestador puede salir de `discover_with_human` solo cuando se cumple uno:

- el humano responde explicitamente que el alcance es suficiente para lanzar
  planners;
- no quedan dudas de objetivo/no objetivo/restricciones y el orquestador
  presenta un resumen final al humano;
- el humano pide avanzar aunque queden dudas, que quedan registradas como
  `OPEN DECISIONS / QUESTIONS FOR HUMAN`.

En el tercer caso, el override humano siempre se persiste como
`human_planning_note`, y el `planning_brief` enviado a planners conserva las
preguntas sin resolver.

Antes de sellar el brief, discovery debe preguntar si Codex review es obligatorio
o presentar un default explicito (`codexReviewRequired: false`) para confirmacion
humana. El campo no puede quedar `undefined`.

### 3. Sesiones

Crear dos tareas `task.assign` y dos sesiones `agent.spawn`:

- Planner A: `claude-code`, role `planner`, modelo definido por
  `client-config/profiles/advanced-planning/mcp.json: draftPlannerAModel`
  (`claude-opus-4-7` solo como default documentado).
- Planner B: modelo distinto. Preferencia: `codex`, role `planner`, modelo
  definido por `client-config/profiles/advanced-planning/mcp.json:
  draftPlannerBModel`, con perfil no-restricted habilitado. Fallback permitido y
  auditado: `claude-code`, role `planner`, modelo distinto definido por el
  perfil si Codex no esta permitido por policy.

Cada planner recibe el mismo brief y debe producir `plan_draft`.
Las llamadas `task.assign` incluyen metadata `planningId` y `phase` para que el
audit del workflow avanzado sea distinguible de otros bucles de planificacion.
Antes de depender de ese metadata, la tarea debe verificar que
`gateway/src/tools/task.js` acepta `metadata`/`context` extensible. Si el schema
es cerrado, B/0/1 debe extender `task.assign` y sus tests antes de usarlo.

El runner debe comparar los modelos resueltos por policy (`AGENT_MODEL_RESOLVED`)
y fallar si ambos planners usan el mismo agente y el mismo modelo.
`AGENT_MODEL_RESOLVED` ya existe como evento auditado del Gateway emitido por
`gateway/src/services/agent_service.js` y cubierto por
`tests/gateway/tool_agent_model.test.js`; esta tarea consume esa evidencia, no
introduce el campo desde cero.

Si no existe fallback permitido que mantenga modelos distintos, el flujo no debe
continuar con dos planners equivalentes. Debe pausar, guardar
`OPEN DECISIONS / QUESTIONS FOR HUMAN`, explicar que no hay segundo modelo
permitido, y pedir al operador una decision: habilitar perfil, aceptar
single-planner degradado, o abortar.

Aceptar modo single-planner degradado requiere override humano explicito. El
workflow persiste `singlePlannerDegraded: true` y la razon en
`human_planning_note`, `plan_synthesis`, `detailed_plan` y el contexto de
`plan.apply`; no puede pasar a detalle sin que el override este presente.

La opcion "habilitar perfil" debe apuntar al knob concreto:
`client-config/profiles/advanced-planning/.env` con
`AGENTS_PROFILE=advanced-planning` y el perfil policy que habilita Codex solo
para repos no restricted. El runbook debe mostrar el comando/env exacto y el
smoke debe cubrir Codex disabled -> fallback/decision humana.

Si un planner falla durante el draft, el flujo no continua silenciosamente con
un unico draft. Debe guardar el error como `plan_draft_error`, resumirlo al
humano, y pedir decision: relanzar planner, aceptar modo single-planner
degradado, o abortar.

### 4. Persistencia

Guardar:

- `artifact.put(kind="planning_brief")`;
- `artifact.put(kind="human_planning_note")` por cada indicacion relevante;
- `artifact.put(kind="plan_draft", producedBy=plannerASessionId)`;
- `artifact.put(kind="plan_draft", producedBy=plannerBSessionId)`.

### 5. Tests

Agregar smoke dry-run que valide:

- fase `discover_with_human` ejercitada con al menos dos turnos simulados;
- dos planners distintos o fallback con modelos resueltos distintos;
- mismo `traceId`;
- dos artefactos `plan_draft`;
- `human_planning_note` y `planning_brief` persistidos;
- audit con `agent.spawn` y `agent.ask` para ambos planners;
- no se usa `agent.delegate` para la fase conversacional.
- Codex disabled -> se muestra knob de perfil o fallback;
- one planner error mid-draft -> se escala al humano.
