# B/0/4 - Detailed plan generation with Codex review

## Quick reference

| Campo | Valor |
|---|---|
| Stage | B - Advanced planning workflow |
| Branch | `feature/V2-B-0-4-detailed-plan-generation` |
| Depende de | B/0/3 |
| Esfuerzo | XL (2-4d) |

## Por que existe?

Tras el OK humano, el sistema debe transformar la sintesis en un plan stage/tarea
detallado. El usuario quiere que Claude genere ese plan y que Codex lo revise por
stage/tarea, avanzando automaticamente por defecto pero transmitiendo cualquier
indicacion humana al planner y reviewer planner.

## Que hay que hacer?

Implementar la generacion detallada:

- Claude escribe el plan stage/tarea como artefacto y, tras approval de apply,
  como archivos `plan/**`.
- Codex revisa cada stage/tarea.
- El orquestador resume progreso al humano en cada stage/tarea.
- Las correcciones se incorporan o se escalan.

La logica vive en `gateway/src/workflows/advanced_planning/detail.js`,
`autoapprove_scope.js`, `session_manager.js`, `human_notes.js` y
`orchestrator.js`.

Por defecto, el perfil avanzado declara
`context.autoApproveScopes: ["plan.apply"]` al invocar el workflow, lo que activa
autoavance acotado para `plan.apply` en scope `plan/**`. Este default solo
aplica a escritura de planes, nunca a pushes, dependencias, codigo productivo,
repos `restricted` ni acciones `NEVER_AUTO`. `AGENTS_AUTOAPPROVE=plan.apply` es
solo una conveniencia del launcher para construir ese campo de contexto; el
operador puede desactivarlo quitando el hint del launcher o enviando el contexto
sin `autoApproveScopes`.

El autoapprove acotado ya existe en Gateway: `PROJECT_V0 Q/0/5` introdujo la
base (`gateway/src/services/approval_service.js`, `gateway/src/config.js` y
`docs/adr/ADR-006-bounded-autoapprove.md`) y `PROJECT_V0 Z/0/4` introdujo el
scope concreto `plan.apply`, cubierto por
`tests/gateway/plan_autoapprove_scope.test.js` y
`tests/gateway/autoapprove_mechanism.test.js`. Stage B no reimplementa esa base:
solo anade aislamiento de perfil, validacion canonica de rutas y pruebas del
flujo avanzado.

Ese default es de perfil/request, no global. El launcher del perfil
advanced-planning puede leer `AGENTS_AUTOAPPROVE=plan.apply`, pero debe
convertirlo en `context.autoApproveScopes: ["plan.apply"]` al invocar la
herramienta MCP. El Gateway guarda ese campo en el estado de la orquestacion y
lo usa solo para approvals de esa session/request. El smoke debe arrancar un
segundo workflow sin `context.autoApproveScopes` en el mismo proceso Gateway y
probar que no hereda autoapprove.

La seleccion de `claude-opus-4-7` para el detail writer es un pin operativo del
perfil avanzado, no una verdad permanente. La configuracion debe resolver el
modelo desde policy/registry y documentar el punto de cambio cuando el operador
quiera actualizar a un modelo Claude posterior.
El knob canonico es
`client-config/profiles/advanced-planning/mcp.json: detailWriterModel`; prompts
y docs no hardcodean el modelo salvo como default documentado, y
`session_manager.js` resuelve el valor final contra policy/registry.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V2-B-0-4-detailed-plan-generation
```

### 2. Plan detallado Claude

Asignar tarea a `claude-code` role `planner`:

- input: `plan_synthesis`, human approval, human notes;
- output: `detailed_plan` con stages, tasks, dependencies, files, tests,
  acceptance criteria y Definition of done.

### 3. Revision Codex por stage/tarea

La revision Codex tiene dos granularidades:

- una revision roll-up por stage, que valida dependencias, orden y coherencia
  entre tareas;
- una revision por cada tarea leaf, que valida objetivo, archivos, tests,
  acceptance criteria y DoD.

Para cada stage y para cada tarea:

- asignar reviewer a Codex cuando policy lo permita;
- pedir verdict: `OK` o `KO`;
- pedir findings y required fixes;
- guardar `stage_review_notes`.

Si Codex esta disabled por policy, el flujo debe:

- registrar denial/fallback;
- usar reviewer alternativo permitido: `claude-code`, role `reviewer`, modelo
  `claude-opus-4-7` por defecto del registry, o `claude-sonnet-4-6` si el perfil
  avanzado lo selecciona explicitamente;
- marcar `reviewerFallback: true` en `stage_review_notes`;
- incluir en el resumen humano: "Codex unavailable; reviewed by Claude fallback";
- marcar decision como `OPEN DECISION` si `planning_brief.codexReviewRequired`
  es `true`.

`codexReviewRequired` se fija durante `discover_with_human`, se persiste en
`planning_brief`, se copia a `plan_synthesis` y viaja en el contexto de approval
`advanced_plan.detail.generate`. El detail loop lo lee antes de aceptar
fallback reviewer. Si el flag es `true` y Codex no esta permitido, no se ejecuta
fallback automaticamente: se guarda `stage_review_notes` con denial, se abre
`OPEN DECISION` y se espera instruccion humana.

La seleccion del modelo reviewer fallback vive en
`client-config/profiles/advanced-planning/mcp.json` como
`reviewerFallbackModel`; `session_manager.js` lo resuelve contra policy/registry
y registra el modelo real mediante `AGENT_MODEL_RESOLVED`.
Por defecto `reviewerFallbackModel` debe resolver a un modelo distinto del
`detailWriterModel` (por ejemplo `claude-sonnet-4-6` si el detail writer usa
Opus). Si policy solo permite el mismo modelo, el workflow marca `OPEN DECISION`
en vez de aceptar una revision fallback con el mismo modelo sin aprobacion
humana explicita.

### 4. Aplicacion automatica por defecto

El flujo puede avanzar automaticamente entre stage/tarea si:

- no hay `OPEN DECISIONS`;
- el reviewer devuelve OK;
- el scope sigue en `plan/**`;
- no hay cambios de policy, pushes, dependencias o codigo productivo.

Si cualquier reviewer devuelve `KO`, el autoavance queda bloqueado. Para
continuar se requiere una correccion seguida de review `OK`, o override humano
explicito guardado como `human_planning_note` con razon y alcance.

Cualquier mensaje nuevo del humano interrumpe la automatizacion: se registra
`human_planning_note`, se transmite al `planner` y al `planner-reviewer` segun el
glosario del workflow (en esta fase: Claude detail writer y Codex reviewer o
fallback), y se reanuda solo tras actualizar la sintesis o el plan.

La politica por defecto es crear una sesion reviewer separada para cada stage
roll-up y otra sesion reviewer separada para cada tarea leaf. Las notas humanas
pendientes se agregan al prompt/contexto de cada sesion nueva. Esta politica
evita depender de sesiones reviewer largas; cualquier modo alternativo debe ser
un flag explicito y traer tests propios antes de activarse.
`session_manager.js` debe tomar un snapshot atomico de `human_planning_note`
pendientes por `(traceId, planningId)` justo antes de cada spawn reviewer. Si una
nota llega entre snapshot y verdict, se reinyecta via nueva sesion o bloquea el
verdict hasta replay auditado.

### 5. Apply controlado

Antes de escribir archivos `plan/**`, pedir `approval.request` con
`action: "plan.apply"`. En el perfil avanzado, el contexto de la orquestacion
incluye `autoApproveScopes: ["plan.apply"]` por defecto para que el Gateway
auto-conceda esa accion si el contexto no es `restricted` y la action no esta en
`NEVER_AUTO`. Si el operador desactiva autoapprove o la policy no lo concede, el
flujo espera approval humano. El smoke debe cubrir ambos modos.

El approval payload debe incluir:

```json
{
  "action": "plan.apply",
  "context": {
    "repo": "agents-orchestrator",
    "scope": "plan/**",
    "targetPaths": ["plan/PROJECT_V2/B/0/00.md"],
    "synthesisArtifactId": "<artifact>",
    "detailedPlanArtifactId": "<artifact>",
    "iterationCount": 1,
    "planningId": "<planning-id>"
  }
}
```

`targetPaths` queda sellado antes del auto-grant. `autoapprove_scope.js`
canonicaliza y valida cada path contra `plan/**`; una escritura fuera de esa
lista, aunque tambien este bajo `plan/**`, requiere nuevo approval.
`detailedPlanArtifactId` identifica la version exacta que se aplica; si el plan
detallado se regenera tras un KO, el workflow debe pedir un nuevo `plan.apply`
con el artifact actualizado.

Antes de aceptar un auto-grant, el flujo debe calcular la lista de rutas objetivo
del apply y verificar que todas estan bajo `plan/**`. Si alguna ruta queda fuera
de `plan/**`, el autoapprove se rechaza o degrada a approval humano explicito.
La validacion usa rutas canonicas: resolver symlinks, normalizar `..`, comparar
contra el path canonico del repo, y rechazar rutas que escapen de `plan/**`
incluyendo variantes por filesystem case-insensitive.

Si un reviewer devuelve `KO` y el humano decide continuar sin review posterior
OK, la excepcion se persiste como `human_planning_note` con campo obligatorio
`override: { kind: "reviewer_ko", stageOrTaskId, scope }`, validado por
`artifact_schema.js`.

Cada stage/tarea tiene un maximo de tres intentos reviewer antes de pausar
autoavance y abrir `OPEN DECISION`, salvo que el cap de coste/tokens se alcance
antes.
Cada intento se persiste en `stage_review_notes.reviewerAttempts` por
`stageOrTaskId`; el contador se reconstruye desde artifacts tras resume.

- [ ] Claude genera plan detallado stage/tarea.
- [ ] Codex revisa cada stage roll-up y cada tarea leaf cuando policy lo permite.
- [ ] Si Codex no esta disponible, fallback reviewer queda nombrado, auditado con
      `reviewerFallback: true` y visible para el humano.
- [ ] Si `codexReviewRequired` es `true` y Codex no esta disponible, el flujo
      abre `OPEN DECISION` y no acepta fallback automaticamente.
- [ ] Reviewer fallback resuelve a un modelo distinto del detail writer o abre
      `OPEN DECISION`.
- [ ] Cada stage/tarea produce resumen al humano.
- [ ] Reviewer `KO` bloquea autoavance salvo review posterior OK u override humano explicito.
- [ ] La automatizacion se detiene ante indicaciones humanas nuevas.
- [ ] El perfil avanzado declara por defecto
      `context.autoApproveScopes: ["plan.apply"]` para invocaciones del
      workflow; `AGENTS_AUTOAPPROVE` solo sirve para que el launcher construya
      ese campo.
- [ ] Autoapprove queda aislado al perfil advanced-planning y no se filtra a otros perfiles.
- [ ] `plan.apply` se respeta antes de escribir archivos y se prueba con
      autoapprove on/off.
- [ ] Autoapprove verifica rutas canonicas bajo `plan/**` y degrada fuera de scope.
- [ ] `plan.apply` incluye `targetPaths` sellado; escrituras fuera del set
      pre-aprobado reentran a approval.
- [ ] `plan.apply` incluye `detailedPlanArtifactId` e `iterationCount` del plan
      detallado aplicado.
- [ ] El test cubre `codexReviewRequired: true` + Codex disabled -> denial sin fallback automatico.
- [ ] Override humano de reviewer `KO` usa artifact estructurado con
      `override.kind: "reviewer_ko"`.
- [ ] Tres intentos reviewer `KO` para el mismo stage/tarea abren `OPEN DECISION`
      y persisten `reviewerAttempts`.
- [ ] La politica por defecto usa una sesion reviewer por stage roll-up y una
      por tarea leaf, con notas humanas inyectadas en cada prompt.
- [ ] Notas humanas que llegan durante spawn reviewer se capturan o replayan
      antes de aceptar verdict.
- [ ] La seleccion de `claude-opus-4-7` queda documentada como pin configurable.
