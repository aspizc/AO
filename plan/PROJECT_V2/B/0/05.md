# B/0/5 - Runbook, smoke and anti-headless regression

## Quick reference

| Campo | Valor |
|---|---|
| Stage | B - Advanced planning workflow |
| Branch | `feature/V2-B-0-5-advanced-planning-smoke` |
| Depende de | B/0/4 |
| Esfuerzo | L (1-2d) |

## Por que existe?

El fallo operativo detectado fue llamar a `agent.delegate` y pensar que eso era
una planificacion interactiva. El cierre del stage debe dejar documentacion,
smoke y tests que hagan visible la diferencia y eviten regresiones.

## Que hay que hacer?

Crear runbook y smoke E2E del workflow avanzado, con dry-run determinista y modo
real opt-in.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V2-B-0-5-advanced-planning-smoke
```

### 2. Runbook

Crear `docs/advanced-planning-runbook.md`:

- pre-requisitos;
- coste/rate limits esperados para dos planners y revisiones por stage/tarea,
  incluyendo formula de peor caso: `2 planners x 3 draft/review rounds + 1
  detail writer + (N stage roll-up reviews + M leaf task reviews) x hasta 3
  reviewer attempts`, politica dry-run-first y cap configurable de coste/tokens
  por orquestacion. Default
  recomendado: `maxModelCalls=120` y `maxTokens=1000000` en
  `client-config/profiles/advanced-planning/mcp.json`; si el launcher expone
  `ADVANCED_PLANNING_MAX_*`, solo convierte esos env vars a campos de perfil o
  contexto. Si se alcanza un cap, autoavance pausa, abre `OPEN DECISION` y
  espera al operador;
- branch dedicada;
- perfil MCP;
- fase humana inicial;
- dual planner;
- cross-review;
- human detail gate;
- detailed plan;
- Codex review por stage/tarea;
- autoavance e interrupciones humanas;
- audit/artifacts;
- troubleshooting.

### 3. Smoke

`scripts/smoke_advanced_planning.mjs` debe:

- correr dry-run por defecto;
- crear trace;
- crear brief humano fixture;
- fallar si el cliente intenta sellar brief con menos de dos turnos humanos o
  sin confirmacion/avance explicito;
- lanzar dos planner sessions con `agent.spawn`;
- usar `agent.ask` para drafts;
- hacer cross-review;
- simular readiness;
- crear approval detail gate;
- simular plan detallado;
- simular review por stage/tarea;
- verificar artifacts y audit.
- verificar que la invocacion advanced-planning lleva
  `context.autoApproveScopes: ["plan.apply"]`, que Gateway lo respeta solo para
  esa session/request, y que un modo opt-out queda pendiente hasta approval
  humano.
- arrancar un workflow no avanzado en el mismo proceso Gateway y verificar que
  no hereda `context.autoApproveScopes`;
- simular un planner que falla en draft y verificar escalado humano;
- simular path hostil (`../`, symlink o escape equivalente) y verificar rechazo
  de autoapprove;
- simular `targetPaths` valido con auto-grant y luego una escritura fuera del
  set pre-aprobado que reentra a approval;
- simular reviewer `KO` y verificar que bloquea autoavance.
- simular tres intentos reviewer `KO` para un stage/tarea y verificar
  `OPEN DECISION`;
El fixture dry-run canonico debe quedar por debajo de
`maxModelCalls=120`.

Modo real opt-in:

```bash
AGENTS_DRY_RUN=0 node scripts/smoke_advanced_planning.mjs
```

### 4. Anti-headless regression

Agregar assertion explicita:

- la fase `discover_with_human`, `dual_draft` y `cross_review` no puede usar
  `agent.delegate`;
- si un runner intenta usar `delegate` para esa fase, el test falla con mensaje
  claro.
- `synthesize`, `readiness_gate` y `human_detail_gate` tampoco deben usar
  `agent.delegate` para razonamiento interactivo o humano-facing. Pueden ser
  computo local determinista del orquestador o `agent.ask` contra sesiones
  vivas, pero no ejecuciones headless opacas.
- el mecanismo de deteccion inspecciona audit events con `phase` y falla si
  aparece cualquier `agent.delegate` asociado a `discover_with_human`,
  `dual_draft`, `cross_review`, `synthesize`, `readiness_gate` o
  `human_detail_gate`. Si el camino de delegate no registra `phase`, B/0/5 debe
  agregar ese campo al wrapper/guard antes de activar el test.
- cada fase interactiva debe demostrar uso positivo de `agent.spawn` y
  `agent.ask`: al menos una sesion spawn por planner y al menos un ask por
  sesion en `dual_draft` y `cross_review`.
- la fase `discover_with_human` debe demostrar al menos dos turnos humanos
  simulados antes de crear `planning_brief`.

## Criterios de aceptacion

- [ ] Runbook explica flujo real y dry-run.
- [ ] Smoke dry-run pasa sin CLIs reales.
- [ ] Modo real es opt-in.
- [ ] Tests fallan si se usa `agent.delegate` para planificacion interactiva.

      planes reales se ajusta segun `N`, `M` y retries esperados.
- [ ] Runbook incluye ejemplo de sizing de caps para un plan pequeno.
