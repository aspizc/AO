# B/0/0 - Advanced planning contract and prompts

## Quick reference

| Campo | Valor |
|---|---|
| Stage | B - Advanced planning workflow |
| Branch | `feature/V2-B-0-0-advanced-planning-contract` |
| Depende de | V0 Z/0/3 |
| Esfuerzo | L (1-2d) |

`V0 Z/0/3` es un predecesor real: aporta el baseline existente de runbook y
smoke para planificacion asistida (`docs/planning-loop-runbook.md` y
`scripts/smoke_planning.mjs`). Stage B usa sesiones ligadas a `task.assign`.
`task.assign` ya existe como herramienta MCP en `gateway/src/tools/task.js` y
esta cubierto por `tests/gateway/tool_orchestration_task.test.js`,
`tests/gateway/mcp_bootstrap.test.js` y `tests/e2e/mcp_two_agent_workflow.test.js`.

## Por que existe?

El flujo de planificacion asistida actual puede ejecutarse con `agent.delegate`,
que es real pero headless. Para una planificacion avanzada, el primer requisito
es conversacional: el orquestador debe entender con el humano la funcionalidad
antes de lanzar planners. Sin un contrato explicito, el sistema puede generar
drafts prematuros o no transmitir indicaciones humanas a los planners.

## Que hay que hacer?

Definir el contrato del workflow avanzado, los prompts por rol y los formatos de
artefacto para descubrimiento humano, drafts, revisiones cruzadas, sintesis,
readiness assessment y plan detallado.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V2-B-0-0-advanced-planning-contract
```

Before opening a PR, verify that local hooks and CI accept the `feature/V2-*`
branch prefix. If the repo enforces another prefix, update Project V2 docs and
task branch names consistently before continuing.

### 2. Contrato del workflow

Crear `docs/advanced-planning-workflow.md` con estas fases:

1. `discover_with_human`: conversacion inicial in-band con el operador.
2. `dual_draft`: lanzar dos planners independientes.
3. `cross_review`: cada planner revisa el draft del otro.
4. `synthesize`: elegir la mejor propuesta y elementos a combinar.
5. `readiness_gate`: ambos planners indican si esta listo para detalle.
6. `human_detail_gate`: explicar la propuesta al humano y pedir OK.
7. `detailed_plan`: Claude genera plan stage/tarea.
8. `codex_stage_review`: Codex revisa cada stage/tarea.
9. `converge`: aplicar correcciones o escalar dudas.

El contrato debe fijar que la fase `discover_with_human` es persistida y
coordinada por el workflow Gateway expuesto via MCP. No se spawnea un agente
hijo para descubrir el alcance inicial: el cliente MCP envia turnos del operador
y el LLM conversacional del cliente conduce la aclaracion; el Gateway guarda
notas, artifacts, preguntas propuestas y estado hasta que el brief esta listo.

Tambien debe definir un limite de iteraciones para `dual_draft` +
`cross_review`: por defecto tres rondas completas. Si tras tres rondas algun
planner mantiene `READY_FOR_DETAIL: no`, el flujo debe pausar automatizacion,
guardar la sintesis con `iterationCount`, y escalar al humano.

### 2.0 Ubicacion de la implementacion

El workflow vive dentro del Gateway, invocado por una herramienta MCP dedicada,
para que trace, artifacts, approvals y policy decisions salgan del mismo
boundary auditado. Durante `discover_with_human`, el Gateway posee persistencia,
artifacts, preguntas propuestas y forwarding, pero no crea una sesion LLM hija:
el LLM conversacional es el cliente MCP que conduce la herramienta con el
operador. Las sesiones LLM Gateway empiezan en `dual_draft` con `agent.spawn`.

Mapa fuente contractual:

- `gateway/src/tools/advanced_planning.js`: entrypoint MCP del workflow.
- `gateway/src/tools/index.js`: registro de la herramienta MCP.
- `gateway/src/workflows/advanced_planning/orchestrator.js`: maquina de fases,
  barreras de interrupcion, autoavance y recovery por `traceId`/`planningId`.
- `gateway/src/workflows/advanced_planning/artifact_schema.js`: validacion de
  `planning_brief`, `plan_draft`, `plan_cross_review`, `plan_synthesis`,
  `human_planning_note`, `detailed_plan` y `stage_review_notes`.
- `gateway/src/workflows/advanced_planning/human_notes.js`: captura,
  deduplicacion y forwarding de notas humanas.
- `gateway/src/workflows/advanced_planning/session_manager.js`: spawn/reuse/
  respawn de planners y reviewers.
- `gateway/src/workflows/advanced_planning/discovery.js`: fase
  `discover_with_human` y construccion de `planning_brief`.
- `gateway/src/workflows/advanced_planning/dual_draft.js`: creacion de tareas,
  sesiones planner y artifacts `plan_draft`.
- `gateway/src/workflows/advanced_planning/cross_review.js`: revision cruzada,
  readiness y retry/respawn de sesiones.
- `gateway/src/workflows/advanced_planning/synthesis.js`: seleccion de mejor
  propuesta, merge instructions, `iterationCount` y
  `revisionWithinIteration`.
- `gateway/src/workflows/advanced_planning/detail.js`: approval
  `advanced_plan.detail.generate`, detail writer Claude y review stage/tarea.
- `gateway/src/workflows/advanced_planning/autoapprove_scope.js`: aislamiento
  por request/session y validacion canonica de rutas `plan/**`.
- `gateway/src/workflows/advanced_planning/converge.js`: aplica correcciones
  derivadas de KO/reviews o escala dudas con artifact `convergence_report`.

El perfil `client-config/profiles/advanced-planning/mcp.json` define estos knobs
contractuales: `draftPlannerAModel`, `draftPlannerBModel`, `detailWriterModel`,
`reviewerFallbackModel`, `autoApproveScopes`, `maxModelCalls` y `maxTokens`.
`session_manager.js` resuelve los modelos contra policy/registry; prompts y docs
solo citan defaults.
Los env vars del launcher, si existen, solo construyen esos campos de perfil o
contexto; no son fuente de verdad dentro del Gateway.

Cada tarea de Stage B debe modificar solo el subconjunto de estos modulos que le
corresponde y enlazar sus acceptance criteria con tests que ejerciten esos
modulos.

B/0/0 solo documenta este mapa en `docs/advanced-planning-workflow.md`; no crea
stubs ni archivos fuente Gateway. La creacion/edicion de esos modulos empieza en
B/0/1 y continua por fase.

### 2.0.1 Aislamiento de autoapprove elegido

Stage B usa aislamiento por request/session, no una variable de entorno global
compartida entre clientes. El perfil advanced-planning puede declarar el default
en su launcher/config, pero el cliente lo transmite como
`context.autoApproveScopes: ["plan.apply"]` al crear o continuar el workflow. El
orquestador guarda ese valor en estado de la orquestacion y lo pasa al approval
path solo para esa session/request.

`AGENTS_AUTOAPPROVE=plan.apply` queda permitido solo como conveniencia del
launcher del perfil para construir ese campo; el Gateway no debe depender de
mutar env global en caliente ni de que dos clientes compartan el mismo proceso.
El smoke debe arrancar dos workflows en el mismo proceso Gateway, uno con
`autoApproveScopes: ["plan.apply"]` y otro sin ese campo, y demostrar que el
segundo no hereda el auto-grant.

Todo `approval.request(action="plan.apply")` emitido por Stage B debe incluir
`context.targetPaths`, una lista sellada de rutas canonicas relativas al repo.
`autoapprove_scope.js` valida `targetPaths` contra `plan/**` antes de cualquier
auto-grant. Si una escritura posterior intenta tocar una ruta fuera de
`targetPaths`, el workflow debe detenerse y pedir un nuevo approval explicito.

Las notas humanas durante autoavance entran por la misma herramienta MCP
`advanced_planning` con evento `operator_message`; el Gateway lo persiste como
`human_planning_note` antes de reanudar fases automatizadas.

Antes de implementar Stage B se debe verificar que `PROJECT_V0 Q/0/5` esta
presente en `gateway/src/services/approval_service.js` y
`tests/gateway/autoapprove_mechanism.test.js`, y que `PROJECT_V0 Z/0/4`
introdujo `plan.apply` con `tests/gateway/plan_autoapprove_scope.test.js`. Si
falta cualquiera de esas bases, B/0/0 documenta bloqueo o dependency formal.

### 2.1 Glosario de roles

El contrato debe mapear la terminologia del operador a roles concretos:

- `planner`: el agente que propone drafts o escribe el plan detallado segun fase.
- `planner-reviewer`: el agente que revisa el draft/plan de otro agente. En la
  fase de draft es el planner opuesto; en la fase detallada es Codex reviewer si
  policy lo permite, o el fallback permitido auditado.
- `orquestador`: el agente humano-facing que conserva la conversacion con el
  operador y transmite notas humanas a planner y planner-reviewer.

### 2.2 Interrupciones humanas

El contrato debe definir el mecanismo de interrupcion durante autoavance. Como
minimo, antes de avanzar de una unidad automatica a la siguiente, el
orquestador debe comprobar un canal auditado de notas humanas:

- mensajes in-band recibidos por el cliente MCP humano-facing;
- `human_planning_note` artifacts pendientes;
- approvals denegados o notas asociadas a approvals.

Si existe una nota nueva, el flujo pausa autoavance, persiste la nota como
`human_planning_note`, la reenvia al planner y planner-reviewer activos o
re-spawneados, y solo continua tras refrescar readiness/synthesis.

Las barreras obligatorias de comprobacion son:

- antes de pasar de `discover_with_human` a `dual_draft`;
- entre `dual_draft` y `cross_review`;
- entre `cross_review` y `synthesize`;
- antes de `readiness_gate`;
- antes de pedir `human_detail_gate`;
- antes de cada review Codex de stage roll-up;
- antes de cada review Codex de tarea leaf;
- antes de cada `approval.request(action="plan.apply")`.

### 2.3 Limites globales

Ademas del limite de tres rondas para `dual_draft -> cross_review -> synthesize`,
el contrato debe fijar un limite global de cinco ciclos de vuelta a
`discover_with_human` por una misma orquestacion. Al llegar al limite, el sistema
debe pausar, resumir bloqueos y pedir decision humana explicita.

`planningId` se asigna cuando `discover_with_human` crea el primer
`planning_brief` y permanece constante para todas las rondas, drafts, syntheses,
detalle y reviews de esa orquestacion. Una orquestacion nueva tras abort
explicito recibe un `planningId` nuevo. La clave de recovery es
`(traceId, planningId)`.

`iterationCount` representa rondas reales `dual_draft -> cross_review ->
synthesize`; no representa versiones de una sintesis dentro de la misma ronda.
Cada `plan_synthesis` incluye `iterationCount` y `revisionWithinIteration`. Una
nota humana durante `cross_review`/`synthesize` crea una nueva version de
`plan_synthesis` con el mismo `iterationCount` y
`revisionWithinIteration + 1`; no consume una ronda del cap de tres. Si el
orquestador reanuda tras crash, reconstruye el contador desde el maximo
`iterationCount` para `(traceId, planningId)` y reconstruye versiones desde
`revisionWithinIteration`.

El limite global de cinco ciclos de vuelta a discovery tambien se cuenta por
`(traceId, planningId)`: se reconstruye contando versiones `planning_brief` con
`phase: "discover_with_human"` y el mismo key de recovery. `artifact_schema.js`
valida `planningId`, `phase`, `discoveryCycle`, `iterationCount` y
`revisionWithinIteration`.

La fase `converge` es real, no solo descriptiva. Entrada: reviewer KO,
correcciones requeridas, override humano o dudas abiertas tras readiness/detail.
Salida: `convergence_report` con acciones aplicadas, artifacts reemplazados,
preguntas abiertas y siguiente fase (`cross_review`, `human_detail_gate`,
`codex_stage_review` o pausa humana). No puede usar `agent.delegate` para
razonamiento humano-facing.

### 3. Prompts

Crear o actualizar prompts:

- `prompts/advanced_planning_orchestrator.md`
- `prompts/advanced_planner_draft.md`
- `prompts/advanced_planner_cross_review.md`
- `prompts/advanced_plan_detail_writer.md`
- `prompts/advanced_plan_stage_reviewer.md`

Los prompts deben exigir:

- resumen al humano en cada iteracion;
- seccion `OPEN DECISIONS / QUESTIONS FOR HUMAN`;
- readiness assessment explicito: `READY_FOR_DETAIL: yes|no`;
- transmission log de indicaciones humanas recibidas;
- prohibicion de escribir archivos desde planners.

`prompts/advanced_planning_orchestrator.md` es el prompt que debe cargar el
cliente MCP humano-facing para conducir `discover_with_human`; el Gateway lo
referencia desde `client-config/profiles/advanced-planning/mcp.json` y valida en
estructura que el perfil lo apunte. El Gateway no asume que el prompt existe
solo porque el archivo este en disco.
El test estructural debe verificar que ese prompt contiene
`discover_with_human`, `operator_message`,
`OPEN DECISIONS / QUESTIONS FOR HUMAN` y prohibicion de escritura directa.
Aunque el LLM viva en el cliente, el Gateway no sella `planning_brief` si no ha
recibido al menos dos turnos de operador y una senal humana de alcance suficiente
o avance explicito.

### 4. Formatos de artefacto

Documentar artefactos esperados:

| Kind | Contenido |
|---|---|
| `planning_brief` | Resumen acordado con humano. |
| `plan_draft` | Draft independiente de cada planner. |
| `plan_cross_review` | Revision del draft del otro planner. |
| `plan_synthesis` | Mejor propuesta, elementos combinados, `iterationCount`, readiness y preguntas abiertas. |
| `human_planning_note` | Indicacion del humano, fase en la que llego, destinatarios reenviados y efecto esperado. |
| `detailed_plan` | Plan stage/tarea generado por Claude. |
| `stage_review_notes` | Revision Codex de cada stage/tarea. |
| `convergence_report` | Correcciones aplicadas, artifacts reemplazados, siguiente fase o pausa. |
