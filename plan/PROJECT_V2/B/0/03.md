# B/0/3 - Human detail review and approval gate

## Quick reference

| Campo | Valor |
|---|---|
| Stage | B - Advanced planning workflow |
| Branch | `feature/V2-B-0-3-human-detail-gate` |
| Depende de | B/0/2 |
| Esfuerzo | M (3-5h) |

## Por que existe?

Aunque ambos planners esten de acuerdo, el sistema no debe generar un plan
detallado sin explicar primero al humano que proyecto se propone construir y
recibir su OK. Esta es la frontera entre exploracion y compromiso de plan.

## Que hay que hacer?

Agregar un gate humano explicito antes de la generacion del plan detallado.
La logica vive en `gateway/src/workflows/advanced_planning/detail.js`,
`orchestrator.js`, `human_notes.js` y `artifact_schema.js`.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V2-B-0-3-human-detail-gate
```

### 2. Resumen humano

El orquestador debe presentar:

- objetivo final;
- arquitectura o workflow propuesto;
- tareas principales;
- tradeoffs;
- riesgos;
- decisiones abiertas;
- recomendacion de los planners;
- que ocurrira si el humano aprueba.

### 3. Approval MCP

Crear approval:

```json
{
  "action": "advanced_plan.detail.generate",
  "context": {
    "repo": "agents-orchestrator",
    "scope": "plan/**",
    "targetPathsEstimate": ["plan/PROJECT_V2/B/**"],
    "synthesisArtifactId": "<artifact>",
    "singlePlannerDegraded": "<from plan_synthesis.singlePlannerDegraded>",
    "codexReviewRequired": "<from planning_brief.codexReviewRequired>",
    "autoApproveScopes": "<from orchestration state>"
  }
}
```

Usar `approval.wait` o `approval.poll`. `pending` o timeout no es aprobacion.
El servicio de approvals acepta acciones arbitrarias; esta tarea debe documentar
`advanced_plan.detail.generate` como action contractual del workflow y cubrirlo
con un test de request/poll/wait para evitar drift del contrato.
Si durante implementacion se detecta una allowlist/registry de actions en
`approval_service.js`, esta tarea debe registrar explicitamente
`advanced_plan.detail.generate` ahi y cubrirlo en el mismo test.

El `scope: "plan/**"` de este approval expresa la intencion de generar solo plan.
B/0/4 sigue siendo responsable de sellar y validar las rutas concretas antes de cualquier
`plan.apply`: canonicaliza paths, rechaza escapes y degrada a approval humano si
el detalle intenta escribir fuera del envelope. `targetPathsEstimate` es
informativo para auditoria; no concede escritura.

### 3.1 Denial path

Si el approval vuelve `denied`:

1. guardar la decision y nota como `human_planning_note`;
2. no generar `detailed_plan`;
3. presentar al humano dos rutas: volver a `discover_with_human` o volver a
   `cross_review` con la nota de rechazo;
4. reenviar la nota a planner y planner-reviewer antes de cualquier nuevo
   readiness;
5. completar o pausar la orquestacion segun indique el humano.

Si el humano vuelve a `discover_with_human`, `planningId` se conserva,
`discoveryCycle` aumenta, los artifacts downstream previos quedan referenciados
como contexto historico pero no como base aprobada, y una nueva ronda
`dual_draft` aumenta `iterationCount` solo cuando se generan drafts nuevos. Si
el humano vuelve a `cross_review`, se conserva el `iterationCount` actual y la
nota de denial produce una nueva `revisionWithinIteration`. Ningun denial
resetea el cap global de cinco discovery cycles para `(traceId, planningId)`.

Las sesiones planner A/B son best-effort durante `human_detail_gate`; no se
asume que sobrevivan a approvals humanos largos. El flujo por defecto para
volver a `cross_review` tras `denied` es re-spawnear los roles equivalentes con
`planning_brief`, `plan_draft`, `plan_cross_review`, `plan_synthesis` y la nota
humana como contexto. Si las sesiones originales siguen vivas, se pueden
reutilizar, pero el workflow no depende de keepalive ni de TTL extendido.

Si llega un `human_planning_note` durante `human_detail_gate`, el workflow debe
asegurar que existe una sesion planner-reviewer disponible antes de afirmar que
la nota fue reenviada: reutiliza la sesion viva o re-spawnea con
`planning_brief`, `plan_draft`, `plan_cross_review`, `plan_synthesis` y la nota.

### 4. Indicaciones humanas

Si el humano da instrucciones nuevas antes o durante el gate:

- guardarlas como `human_planning_note`;
- reenviarlas al planner y al planner-reviewer segun el glosario del workflow;
- pedir confirmation/update de readiness;
- crear una nueva version de `plan_synthesis`.

## Criterios de aceptacion

- [ ] El plan detallado no se genera sin approval concedido.
- [ ] Timeout/pending no cuentan como aprobacion.
- [ ] `denied` vuelve a discovery o cross-review y nunca avanza a detalle.
- [ ] `denied` preserva `planningId`, actualiza `discoveryCycle` o
      `revisionWithinIteration` segun ruta, y no resetea caps.
- [ ] Planner/planner-reviewer se re-spawnean con contexto por defecto tras
      approvals largos o denegados; sesiones vivas son solo optimizacion.
- [ ] Nota humana durante `human_detail_gate` con planner-reviewer expirado
      re-spawnea antes de reenviar.
- [ ] Las indicaciones humanas se guardan y se transmiten al planner y al planner-reviewer.
- [ ] El resumen humano incluye riesgos y decisiones abiertas.
- [ ] `advanced_plan.detail.generate` queda documentado y probado como action.
- [ ] El gate humano muestra `singlePlannerDegraded` si aplica antes de aprobar detalle.
