## Por que existe?

Dos drafts independientes no bastan. Cada planner debe criticar el trabajo del
otro, comparar alternativas y decidir si la propuesta esta lista para generar un
plan detallado o necesita otra ronda con el humano.

## Que hay que hacer?

Implementar la ronda de revision cruzada y sintesis:

- Planner A revisa draft B.
- Planner B revisa draft A.
- El orquestador sintetiza mejor propuesta, elementos a combinar y correcciones.
- Ambos planners emiten `READY_FOR_DETAIL: yes|no`.

La logica se implementa principalmente en
`gateway/src/workflows/advanced_planning/cross_review.js`, `synthesis.js`,
`human_notes.js` y `session_manager.js`, invocada desde `orchestrator.js`.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V2-B-0-2-planner-cross-review
```

### 2. Cross-review

Usar `agent.ask` sobre sesiones planner disponibles, no `delegate`, para pedir:

- principales aciertos del draft revisado;
- principales riesgos;
- elementos que deben corregirse;
- elementos que conviene combinar;
- eleccion razonada de la mejor base;
- `READY_FOR_DETAIL: yes|no`.

Guardar dos artefactos `plan_cross_review`.

### 2.1 Ciclo de vida de sesiones

B/0/2 no asume que las sesiones creadas en B/0/1 sobreviven entre iteraciones.
La politica por defecto es:

1. intentar reutilizar la sesion planner si `session.view` o el estado Gateway
   indica que sigue viva;
2. si expiro, fue cerrada o no existe en recovery, re-spawnear el rol
   equivalente con `planning_brief`, ambos `plan_draft`, `human_planning_note`
   pendientes y contexto de iteracion;
3. guardar en audit/artifact metadata si la revision uso `sessionReused: true`
   o `sessionRespawned: true`;
4. no usar keepalive artificial como requisito de correccion.

### 3. Sintesis

Crear `plan_synthesis` con:

- recommended base: planner A, planner B, or combined;
- merge instructions;
- required corrections;
- unresolved human questions;
- readiness result;
- `iterationCount`;
- `revisionWithinIteration`;
- `humanNotesApplied`.

`humanNotesApplied` es un array de artifact ids, o de objetos `{ id, phase }`,
que referencian `human_planning_note` aplicadas a esa sintesis. El schema en
`artifact_schema.js` debe rechazar una sintesis que declare notas aplicadas sin
ids auditables.

Si ambos planners dicen `READY_FOR_DETAIL: yes`, el flujo puede pasar al gate
humano. Si alguno dice `no`, el orquestador resume al humano y abre una nueva
iteracion de discovery/draft/review.

El orquestador emite un audit event explicito con `phase: "readiness_gate"`
despues de construir `plan_synthesis` y antes de decidir si avanza a
`human_detail_gate`; la regression anti-headless usa ese marker.

### 3.1 Indicaciones humanas durante cross-review

Si el humano envia una indicacion durante `cross_review` o `synthesize`, el
orquestador debe:

1. guardar `artifact.put(kind="human_planning_note")` con fase,
   destinatarios y contenido;
2. reenviar la nota a ambas sesiones planner con `agent.ask`;
3. pedir a ambos planners un nuevo `READY_FOR_DETAIL: yes|no`;
4. crear una nueva version de `plan_synthesis` en vez de mutar la anterior, con
   el mismo `iterationCount` y `revisionWithinIteration + 1`;
5. resumir al humano que cambio antes de continuar.

### 3.2 Limite de iteraciones

El workflow permite por defecto tres rondas completas
`dual_draft -> cross_review -> synthesize`. Si al cerrar la tercera ronda algun
planner responde `READY_FOR_DETAIL: no`, el sistema debe pausar autoavance,
guardar `plan_synthesis` con `iterationCount: 3`, abrir
`OPEN DECISIONS / QUESTIONS FOR HUMAN`, y esperar indicacion humana.

### 4. Tests

El smoke debe simular:

- A ready + B ready -> avanzar a human detail gate;
- A ready + B not ready -> no avanzar;
- open decisions -> no avanzar sin resumen humano.
- human note during cross-review -> ambos planners reciben la nota y se crea una
  nueva sintesis sin avanzar `iterationCount`;
- expired planner session during cross-review -> se re-spawnea con brief+drafts
  y la revision continua auditada;
- crash mid-synthesis -> resume -> `iterationCount` se reconstruye desde los
  `plan_synthesis` previos para `(traceId, planningId)`;
- iteration cap reached -> autoavance pausado y escalado al humano.

## Criterios de aceptacion

- [ ] Cada planner revisa el draft del otro.
- [ ] Se guardan dos `plan_cross_review`.
- [ ] Se guarda un `plan_synthesis`.
- [ ] El avance a detalle requiere readiness positivo de ambos planners.
- [ ] Se emite audit event `phase: "readiness_gate"`.
- [ ] Las decisiones abiertas se resumen al humano.
- [ ] Las indicaciones humanas durante cross-review se reenvian a ambos planners.
- [ ] Si una sesion planner expiro, se re-spawnea con contexto y queda auditado.
- [ ] El limite de iteraciones queda persistido y probado.
- [ ] `iterationCount` se reconstruye desde artifacts tras resume/crash.
