# A/0/02 — Persistent SDK wave dispatch and supervised phases

| Field | Value |
|---|---|
| Status | `planned` |
| Functional priority | P0 — dependency-ready work shares a persistent Gateway |
| Depends on | V7 A/0/00, A/0/01; reviewed/integrated V6 A/0/04 |
| Blocks | V7 A/0/03 |
| absorbed_from | V6 generic wave requirement; overlaps V5 H/0/02 and F/0/04 without closing their gates |
| Review id | `A_0_2` |

## Problem

The KYA script launches a Gateway for each request and delegates iterative
work. A generic wave needs persistent supervised sessions, deterministic
admission and errors, and explicit review input without claiming integration.

## Scope and execution contract

Add `wave_runner.py` and `agent-run wave run --profile <path> --wave <id>
--budget <path> --runtime-root <path> --control-dir <path>
[--prior-wave-facts <path>] --json`, with the
gateway/policy/allowed-root bindings defined in A/0/00. Validate before any
effect. Generate one UUID `runId`; reserve a Gateway slot, then enter the
existing `GatewayClient` once for the selected wave. Initialize once, verify
required `tools/list` entries, and retain that connection across all tasks.
An injected initialized client is borrowed and never exited by the runner;
all runner-created sessions/checks still have explicit ownership. CLI uses
managed stdio only. No stdio attach, second transport, daemon or new MCP tool.
Each reservation includes its mandatory declared memory from A/0/00 in
A/0/01's same atomic vector; memory denial prevents SDK/spawn/check startup.
Borrowed Gateway capacity remains the embedding owner's reservation; this run
neither charges it a second time nor releases it. The embedding contract must
supply its known reservation reference in the same budget, or reject the
topology before dispatch.

State per logical task: `pending`, `coding`, `awaiting_handoff`, `checking`,
`reviewing`, `awaiting_review`, `cleanup`, `externally_accepted`, `blocked`, `failed`,
`cancelled`, or `recovery_required`. Attempts are integers 1–`maxTrials`.
Admit in declared task order only after all dependencies are
`externally_accepted`, the number of held logical task slots is strictly below
the selected wave's `maxConcurrentTasks`, available capacity is reserved, and
no active task conflicts. Conflict means equal `conflictKeys` or canonical overlapping
write paths (same path or parent/child); conservatively serialize across the
entire coding/check/review phase. Different task IDs do not establish safety.
Task-local failures block its dependents; unrelated admitted tasks continue.

Acquire one logical slot when admitting a task before its first effect; expose
`admissionHeld` in its task DTO. The slot covers coding, awaiting handoff,
checking, reviewing, awaiting review and cleanup, including time spent waiting
for control/capacity between those phases. Waiting does not start another
attempt or consume a trial. A `recovery_required` task with possible active
effects retains its slot and conflicts. Release the slot only after all of
that attempt's owned effects have confirmed retirement and their reservations
have been released, then set the terminal disposition. A task blocked before
admission holds no slot. A rejected reservation with known zero effects may
undo a provisional admission without consuming an attempt. Explicit retry
must reacquire a slot after confirmed prior retirement; global capacity never
substitutes for this per-wave ceiling. A/0/03 persists the held-slot flag so
recovery cannot make uncertain active work disappear from the count.

## Earlier-wave readiness input

Dispatch only tasks in the selected wave. Supply exactly the earlier-wave
dependencies directly referenced by those tasks through
`--prior-wave-facts`; the already-authorized parent may derive this document
deterministically from preceding local result envelopes. A wave with no earlier
dependencies needs no document; no directory scan, implicit latest-run lookup
or Gateway/review authority follows from supplied history.

Closed `wave-prior-facts/v1` input: `{schemaVersion, projectId, profileDigest,
facts}`; at most 256 facts and 256 KiB, UTF-8 regular file within an explicit
allowed root, no symlink or unknown fields. Each fact has exactly
`sourceRunId` (UUID), `sourceWaveId`, `taskId`, `attempt` (1–`maxTrials`),
`sourceWaveStatus`, `taskStatus`, `resultDigest`, `reviewEventId`,
`candidateDigest`, `ownedCleanupConfirmed`. Status fields allow
`externally_accepted`, `blocked`, `failed`, `cancelled`, `recovery_required`.
Digests are `sha256:` plus 64 lowercase hex; `resultDigest` references the
canonical historical `wave-result/v1` bytes. Receipt ID is UUID or null;
candidate digest is the same digest shape or null; cleanup is boolean.
This reference is a controller-supplied historical fact, not verification of
the source result, candidate freshness or an authentic review verdict.

Current project/profile digest must match. Every task occurs exactly once in
the required set and belongs to its stated earlier wave in this profile.
Facts for one source wave use one consistent source run/result digest/status.
Success readiness requires source wave and task both `externally_accepted`,
nonnull matching-format review/candidate references and confirmed owned
cleanup. Failed/blocked/cancelled/recovery source work keeps its dependent
blocked with no new attempt. Missing required facts yield
`WAVE_PRIOR_FACTS_MISSING` (exit 5); malformed input yields
`WAVE_INPUT_INVALID` (exit 2); contradictory project/profile/membership,
duplicate conflicting history or inconsistent success fields yield
`WAVE_PRIOR_FACTS_CONFLICT` (exit 2), before Gateway startup. Matching negative
history is valid input: unrelated selected-wave tasks may proceed, but its
dependent cannot spawn. Persist accepted input and its SHA-256 normalized
digest for resume; changed facts are a checkpoint conflict, never prior replay.

For each attempt, create a fresh trace. Explicitly supply profile orchestrator
identity on create/assign, and returned trace/task/session IDs on every call.
Never set a mutable client-wide trace default while tasks run concurrently.
Assign coder `code.write` before `agent.spawn`; send the bounded coder prompt
using `agent.ask`; inspect with bounded `agent.view`. No `agent.delegate`, raw
tmux keystrokes, model routing, menu decision, or pane-text completion inference.
The coder brief states the repository's 20000-token task budget and required
handoff; V7 does not claim token metering.

External handoff triggers declared checks. Each check reserves capacity and
executes its argv with `shell=False`, validated cwd and monotonic timeout;
stdout/stderr go to DEVNULL, with only check ID, exit code, timeout and duration
in the result. No shell interpolation or echoed argv/prompt/output. On timeout,
terminate/reap the owned direct child and report failure; descendants are a V5
containment residual, not proven retired. If direct-child exit is unknown,
retain capacity and mark recovery required. Nonzero checks block review.

Close the known coder session before releasing its session/provider slots and
starting the separately assigned reviewer. Assign reviewer
`artifact.put.review_notes`, reserve new slots, `spawn/ask/view` with its
explicit selection, and require a different returned session ID. Read-only
review requires existing policy to allow that action/session; a denial is
reported, never converted into reviewer `code.write`. Review prompt includes
only configured bounded evidence references and handoff metadata. V7 does not
copy raw restricted artifacts into the review prompt. Generic templates retain
working rules and consume explicit project fields, not KYA assumptions.

## External input and outputs

`wave-control/v1` files are local controller input in the explicitly configured
control directory. The already-assigned parent orchestrator may generate them
automatically within its existing project review/execution authority after
reading evidence from the distinct reviewer; the operator may supply them as
well. No new human confirmation or manual file-writing step is required per
task. Configured project/policy human gates stay pending until the appropriate
existing human decision; this protocol does not add, waive, or grant authority
for those gates. At most 64 KiB, regular files contained in that
directory, no symlink/unknown field; process by UUID `eventId`, once per run.
Closed common fields: `schemaVersion`, `eventId`, `runId`, logical `taskId`,
`attempt`, `kind`. Exact variants:

- `handoff`: `coderSessionId`, `candidateDigest` (`sha256:` plus 64 lowercase
  hex), `evidenceRef` (bounded relative path under configured review directory).
- `review`: same digest, `reviewerSessionId`, `evidenceRef`, and
  `decision` = `accepted`, `changes_requested`, or `blocked`.
- `retry`: the preceding attempt and `nextAttempt` exactly one greater.
- `cancel`: task ID or null for the wave, and a bounded stable reason code.

Receipts must match the current run/task/attempt, returned session identities
and most recent handoff digest. A receipt cannot create a task, authorize a
Gateway operation, change policy or certify the source. The authorized parent
controller interprets distinct reviewer evidence and provides the explicit
review decision; it cannot replace that reviewer with a verdict on its own
code. The runner does not infer acceptance from a pane banner, artifact kind or
coordination message. Evidence supplies facts, not review authority. Reject
stale/duplicate-ID with different-content receipts as `WAVE_INPUT_CONFLICT`; malformed input is
`WAVE_INPUT_INVALID`, without echoing its content. Same event/content is inert.

`changes_requested` requests a blocked disposition and retirement of the known
review session through the finalizer below. The authorized parent may issue explicit `retry` under existing
project authority without a new human confirmation; configured human gates
and trial exhaustion still apply. Only that control event admits the next
attempt, with fresh trace and sessions after confirmed prior cleanup;
15 attempts is the hard maximum.
Exhaustion returns `WAVE_TRIALS_EXHAUSTED` and requires operator action.
Ambiguous spawn/ask/check never automatically retries, even after timeout.

For each matching review decision, first record its receipt and pending
disposition (`externally_accepted` for accepted, `blocked` otherwise), then
enter `cleanup` while holding the logical slot. Close the exact owned reviewer
using `agent.kill` with its recorded trace/session binding. Reject tool/body
errors, missing/false `closed`, or contradictory response shape. Only validated
close confirmation permits release of its complete session/provider/memory
reservation. Confirm every remaining owned check/session is retired and its
reservation released, then set the terminal disposition, release the logical
slot and admit eligible dependents. Apply the same finalizer to `blocked` and
`changes_requested`; neither input proves retirement or starts a retry. An
uncertain/failed close or reservation release returns `recovery_required`,
retains the pending decision, logical slot and any unreleased vector, and does
not expose terminal acceptance. A/0/03 records kill/release intent and confirmed
outcomes; a receipt alone never frees resource or logical capacity.

`wave-result/v1`: `{schemaVersion, runId, projectId, waveId, profileDigest,
status, tasks, resources, outcomeCode}`. `status` is `running`,
`awaiting_input`, `externally_accepted`, `blocked`, `failed`, `cancelled`, or
`recovery_required`. Task DTOs expose ID, attempt, phase, known Gateway IDs,
safe check metadata, receipt IDs and outcome codes. Resource DTOs expose
reservation IDs, ownership flags and safe counters only. Task DTOs also expose
`admissionHeld` and nullable `pendingDisposition`; result exposes the normalized
`priorFactsDigest` or null. No prompt, pane, token, stdout/stderr,
argv, attachment command, arbitrary metadata or raw error payload is returned.
Known Gateway tool responses pass `raise_on_tool_error()` and shape validation;
MCP `isError`, JSON body errors, malformed results, and missing IDs are failures.
Raw exception/result repr must not escape CLI rendering.

All terminal accepted tasks and successful wave exit checks enter wave exit
cleanup. After confirmed retirement/release of every owned task/check resource,
close the owned SDK client/context and validate successful closure before
releasing the owned Gateway's complete count/memory reservation. Only confirmed
SDK closure and reservation release permit final `externally_accepted`/exit 0.
A closure/release error or lost outcome instead yields `recovery_required`/exit
5 with explicit held references; do not return success with an unreported hold.
Borrowed SDK client and Gateway reservation remain with their owner and are
reported as borrowed, never closed/released by this runner. Their known borrowed
hold does not imply failed cleanup of this run's owned effects.
No `orchestration.complete`, merge, push or tag
is automatically called; this outcome is neither V5 review closure nor release.
On cancellation/error, close only known runner-created sessions/SDK clients and
owned direct check handles; failed cleanup retains reservations and produces
`recovery_required`. A failed task cannot close another task's session or the
shared Gateway. Output JSON is one final envelope; bounded safe progress goes
to stderr. Awaiting external input can stop after a configured operator
deadline without claiming success; waiting never consumes a provider retry.
Freeze `--input-timeout-ms` as integer 1000–3600000, default `60000`, one
monotonic deadline per awaiting-input phase. Timeout returns `awaiting_input`;
this leaf closes known owned sessions before exit and reports that closure.
Hold the logical slot throughout that cleanup; after confirmed full retirement
and release the task is `blocked` with `WAVE_INPUT_TIMEOUT`, not an active phase
with a freed slot. The wave's `awaiting_input` outcome then needs explicit
controller input for any next attempt; timeout never creates it automatically.
A/0/03 may persist/preserve sessions for explicit resume instead, recording that
behavior and holding their reservations and logical slots; it must never
silently abandon them.

Stable errors: `WAVE_PREREQUISITE_UNAVAILABLE`, `WAVE_TOOL_FAILED`,
`WAVE_RESPONSE_INVALID`, `WAVE_EFFECT_UNCERTAIN`, `WAVE_CHECK_FAILED`,
`WAVE_INPUT_INVALID`, `WAVE_INPUT_CONFLICT`, `WAVE_TRIALS_EXHAUSTED`.
Confirmed timeout retirement uses `WAVE_INPUT_TIMEOUT` with wave
`awaiting_input`/exit 4; uncertain retirement still uses recovery required.
Prior-input codes are `WAVE_PRIOR_FACTS_MISSING` and
`WAVE_PRIOR_FACTS_CONFLICT`; uncertain retirement uses
`WAVE_EFFECT_UNCERTAIN` with final `recovery_required`.
Reuse A/0/01's `wave-error/v1` projection. CLI exits: `0` externally accepted,
`2` invalid input, `3` unavailable runtime/prerequisite, `4` waiting/capacity,
`5` blocked/recovery, `1` check/tool failure. A/0/03 adds durable run recovery;
this leaf does not claim survival of runner/process restart.

## Non-scope

No automatic worktree creation/integration, model evaluation of deterministic
statuses, independent-verdict authentication, exact candidate freshness,
V5 completion gate, borrowed-client shutdown, or automatic replay.

## Acceptance criteria

- [ ] Multiple task traces execute on one initialized SDK connection.
- [ ] Earlier-wave dependencies use explicit matched historical facts; missing
      or negative facts cannot create readiness, and prior tasks never replay.
- [ ] `maxConcurrentTasks` bounds logical admissions through awaiting control,
      cleanup and unresolved recovery even when shared capacity admits more.
- [ ] Dependencies, conflicts, capacity and check outcomes control actual
      dispatch; provider/check errors cannot become acceptance.
- [ ] Distinct supervised coder/reviewer sessions and explicit consistent
      review receipts precede local external acceptance.
- [ ] The assigned parent can provide review/retry control within existing
      authority after distinct reviewer evidence, without per-task human
      confirmation; configured human gates and trial limits stay binding.
- [ ] Declared Gateway/session/check memory is reserved atomically with count
      capacity, and memory exhaustion starts no corresponding effect.
- [ ] Unknown outcomes have zero replay; retries require explicit input and
      fresh identity, within 15 attempts.
- [ ] Task failures preserve other work; cleanup targets only owned resources
      and uncertain cleanup retains capacity.
- [ ] Accepted/blocked reviewer retirement precedes complete reservation/slot
      release; final success requires owned SDK closure then Gateway release.
- [ ] Safe outputs contain no secret/raw response canaries or review/release
      claims beyond externally supplied local acceptance.
