## Problem

Caller-supplied agent, role, repository, task, and trace values can be confused
with server-established authority or target identity.

## Scope

- Establish a connection/request `RequestContext` with authenticated principal,
  audience, capabilities, trace, task, and canonical realpath repository.
- Derive effective bindings server-side and treat caller identity/repo fields as
  assertions that may deny, never grant.
- Resolve actions through the canonical closed catalog; a missing, unknown, or
  version-skewed action is an explicit `DENY`, never a default policy path.
- Enforce capability, lineage, revocation, and cross-context checks before side
  effects.

## Non-scope

- No public child/reviewer bearer handles, implicit trust from coordination
  presence, fail-open compatibility for new actions, or authorization encoded
  only in prompts.

## Acceptance criteria

- [ ] Effective principal and repository are server-derived.
- [ ] Actor and target role are distinct and policy-visible.
- [ ] Every unknown or unregistered action returns `DENY` before side effects.
- [ ] Cross-trace/task/repo requests fail before launch or persistence.
- [ ] Child/reviewer capabilities never leave internal channels.
