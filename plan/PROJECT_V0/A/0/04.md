## ¿Por que esta tarea existe?

Sin un documento de arquitectura corto y unos ADRs explicitos, las tareas posteriores van a re-interpretar V4. Tres errores tipicos a prevenir:

1. Crear un proceso "orchestrator" como componente.
2. Saltarse policy desde adapters porque "el flujo lo permite".
3. Mezclar tools (capa MCP) con services (logica) sin frontera clara.

Los ADRs (Architecture Decision Records) son contratos cortos y verificables que cualquier task posterior puede citar.

## ¿Que hay que hacer?

Escribir `docs/architecture.md` (≤ 1 pagina), tres ADRs (`ADR-001`, `ADR-002`, `ADR-003`) y una tabla de mapping con `gemini-orchestrator` (que archivo se portara en H/I).

### 2. `docs/architecture.md`

Estructura minima (no mas de 1 pagina pantalla):

```markdown
# Architecture (V4 — implementation view)

## Layers

```
tools/      → expose MCP tools, validate input, delegate to services/
services/   → orchestrate use cases (assign task, delegate agent, share artifact, ...)
core/       → policy_engine, registry, state, audit, sanitizer, ids, artifact_store
adapters/   → spawn CLI subprocesses + tmux. No MCP awareness.
infra/      → SQLite driver, filesystem helpers, env config
```

Forbidden imports:

- `adapters/` MUST NOT import from `tools/`.
- `core/policy_engine` MUST NOT call any LLM.
- No tool may bypass `policy_engine.evaluate(...)`.

## MCP call lifecycle

```
client (any MCP host) ──stdin/stdout──▶ mcp_server.js
                                         │
                                         ▼
                                  tools/<tool>.js
                                         │ Zod validate
                                         ▼
                              services/<use_case>.js
                                  ├─ policy.evaluate
                                  ├─ adapter.<op>      (if needed)
                                  ├─ state.<repo>.<op>
                                  └─ audit.append
                                         │
                                         ▼
                                response (or MCP error)
```

## What does NOT exist (intentionally)

- A standalone `orchestrator/` directory or process.
- Direct child-to-child channels.
- Special policy bypass for the orchestrator role.
- Cursor or Antigravity IDE specific configuration.
```

### 3. ADRs

#### `docs/adr/ADR-001-gateway-only.md`

```markdown
# ADR-001 — Gateway is the only enforcement point

Date: <today>
Status: accepted

## Context
V4 concentrates security real (policy, audit, sanitization, mediation) in
one component: the MCP Gateway. Distributing checks across adapters or
services would create bypass surface.

## Decision
Every action that can affect a repo, an artifact, or another agent MUST
pass through `policy_engine.evaluate(...)` invoked from a service. Tools
delegate to services; services delegate to core/adapters. Adapters never
shortcut policy.

## Consequences
- One place to audit, harden and reason about.
- Adapters stay dumb: `cwd` guard + spawn + tmux + dry-run.
- Future deterministic orchestrator (LangGraph) becomes a peer client.
```

#### `docs/adr/ADR-002-no-orchestrator-component.md`

```markdown
# ADR-002 — Orchestrator is a role, not a component

Date: <today>
Status: accepted

## Context
The "orchestrator" was almost made into a Python process in V3. V4 makes
it explicit: orchestration intelligence lives in the human-facing LLM
(Gemini CLI, Claude Code, Codex, etc.) acting in role `orchestrator`.

## Decision
There is NO directory named `orchestrator/`. There is NO long-running
"orchestrator" process. The Gateway exposes MCP tools; the LLM uses
them. Period.

## Consequences
- We do not duplicate planning intelligence.
- The role `orchestrator` has no privileged access (denied: `code.write`,
  `artifact.get.raw_restricted`, `code.read.raw_restricted`).
- Substitutability is preserved: a deterministic LangGraph client can
  replace the LLM later without changing the Gateway contract.
```

#### `docs/adr/ADR-003-policy-before-spawn.md`

```markdown
# ADR-003 — Policy gate runs before any process spawn

Date: <today>
Status: accepted

## Context
If an adapter spawns a CLI before the policy engine evaluates the
request, the system has already leaked an action. Even a denied later
result does not undo the spawn.

## Decision
Adapters MUST consult `policy_engine.evaluate(...)` BEFORE any
`spawn`/`delegate` call. If the decision is `deny` or
`require_approval` (without a granted approval), the adapter MUST NOT
start the subprocess and MUST emit an audit `POLICY_DECIDED`.

## Consequences
- Adapters are coupled to policy via dependency injection.
- Tests must include "policy denies, no spawn occurs" as a regression
  case for every adapter.
- Bypass attempts via direct cwd or env are caught by `assertSafeCwd`
  and policy redundantly.
```
