## ¿Por que esta tarea existe?

Hasta ahora cada tarea verifica con comandos manuales. Necesitamos un **unico comando** que el operador (y cualquier futuro PR) pueda correr para saber si el repo esta en verde:

```bash
./scripts/ci.sh
```

Ese script sera el "CI local" mientras no haya CI remota. Es tambien el gate que U/0/3 ejecutara para cerrar el MVP.

## ¿Que hay que hacer?

Crear `scripts/ci.sh` que ejecute en orden: estructura, gateway tests, CLI tests; opcionalmente un workflow GitHub Actions equivalente; documentar en README.

## Pre-requisitos

- [ ] A/0/2 (gateway scaffold) y A/0/3 (cli scaffold) mergeadas o disponibles.
- [ ] A/0/4 (docs) mergeada.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/A-0-5-first-green-ci
```

### 2. `scripts/ci.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

REPO_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
cd "$REPO_ROOT"

echo "==> Structure tests (pytest)"
if command -v pytest >/dev/null 2>&1; then
  pytest tests/structure
else
  echo "pytest not found; activate the cli venv first"
  exit 2
fi

echo "==> Gateway tests (node --test)"
if [ -d gateway/node_modules ]; then
  npm --prefix gateway test
else
  echo "gateway/node_modules missing; running 'npm --prefix gateway install' first"
  npm --prefix gateway install
  npm --prefix gateway test
fi

echo "==> CLI tests (pytest)"
pytest tests/cli

echo "==> All checks passed."
```

```bash
chmod +x scripts/ci.sh
```

### 4. (Opcional) `.github/workflows/ci.yml`

Si el operador quiere CI remota (sin push automatico):

```yaml
name: ci

on:
  pull_request:
    branches: [develop, main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "20" }
      - uses: actions/setup-python@v5
        with: { python-version: "3.11" }
      - run: pip install -e "cli[dev]"
      - run: npm --prefix gateway install
      - run: ./scripts/ci.sh
```

### 5. Test que el script existe

`tests/structure/test_ci_script.py`:

```python
from pathlib import Path

REPO = Path(__file__).resolve().parents[2]


def test_ci_script_exists():
    assert (REPO / "scripts" / "ci.sh").is_file()


def test_ci_script_mentions_gateway_and_cli_tests():
    text = (REPO / "scripts" / "ci.sh").read_text(encoding="utf-8")
    assert "gateway" in text
    assert "tests/cli" in text
    assert "tests/structure" in text


def test_ci_script_is_executable():
    import os
    path = REPO / "scripts" / "ci.sh"
    assert os.access(path, os.X_OK)
```

## Errores comunes a evitar

- ❌ Que el script termine con codigo 0 cuando un sub-comando fallo. `set -euo pipefail` lo evita; no lo quites.
- ❌ Hacer `npm install` con red restringida sin documentarlo. Si la red no permite, dejar el script que falle con mensaje claro.
- ❌ Asumir que `pytest` esta en el PATH global. Documenta el `pip install -e cli[dev]`.
- ❌ Anadir steps que requieran credenciales (npm publish, deploys).
