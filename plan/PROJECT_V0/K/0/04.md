# K/0/4 - Two-agent MCP usability flow

## Quick reference

| Campo | Valor |
|---|---|
| Stage | K - Agent tools |
| Branch | `feature/K-0-4-two-agent-mcp-usability-flow` |
| Depende de | K/0/3, N/0/2, Q/0/4, T/0/2 |
| Esfuerzo | M (4-6h) |

## Por que existe?

K/0/3 hace visibles las tools `agent.*`. Esta tarea prueba el caso de uso real
que el operador quiere: un LLM en rol `orchestrator` crea una tarea para un
codificador y otra para un revisor, ambos hijos se ejecutan por MCP, los
artefactos cruzan por Gateway, y el reviewer solo ve material sanitizado.

El test debe usar el Gateway MCP stdio real. No vale llamar directamente a
`services.*` como hace el E2E historico.

## Que hay que hacer?

Crear un E2E MCP de dos agentes:

```text
claude-code/orchestrator
  -> task.assign gemini-cli/restricted-coder
  -> agent.spawn or agent.delegate coder
  -> artifact.put raw_diff restricted
  -> artifact.share to claude-code/reviewer
  -> task.assign claude-code/reviewer
  -> agent.delegate reviewer with sanitized artifact
  -> artifact.put review_notes
  -> approval.request / approval.respond
  -> orchestration.complete
```

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/K-0-4-two-agent-mcp-usability-flow
```

### 2. MCP test harness

Crear o extender un helper en `tests/e2e/helpers/` que pueda:

- arrancar `gateway/src/mcp_server.js` como subprocess stdio;
- enviar `initialize`, `notifications/initialized`, `tools/list` y
  `tools/call`;
- capturar stderr sin contaminar stdout;
- limpiar workspace temporal.

No usar los services internos.

### 3. Test principal

Crear `tests/e2e/mcp_two_agent_workflow.test.js` con un flujo dry-run:

1. Workspace temporal con repos permitidos bajo `AGENTS_REPO_ROOTS`.
2. `AGENTS_DRY_RUN=1`.
3. `orchestration.create` con `callerAgent=claude-code`,
   `callerRole=orchestrator`.
4. `task.assign` a `gemini-cli/restricted-coder` sobre `cvision`.
5. `agent.spawn` o `agent.delegate` del coder con el `taskId` real.
6. `artifact.put` de `raw_diff` `restricted` producido por la sesion coder.
7. `artifact.get` como orchestrator debe devolver `POLICY_DENIED`.
8. `artifact.share` para `claude-code/reviewer` debe crear version sanitizada.
9. `task.assign` a `claude-code/reviewer` con accion de revision.
10. `agent.delegate` del reviewer usando solo contenido sanitizado.
11. `artifact.put` de `review_notes`.
12. `approval.request` y `approval.respond`.
13. `orchestration.complete`.

El test debe afirmar que:

- no aparece el secreto fake en ningun payload visible por orchestrator o
  reviewer;
- existen al menos dos `SESSION_STARTED`, uno para coder y otro para reviewer;
- audit contiene `ORCHESTRATION_CREATED`, `TASK_CREATED`,
  `SESSION_STARTED`, `ARTIFACT_CREATED`, `SANITIZATION_APPLIED`,
  `ARTIFACT_SHARED`, `APPROVAL_REQUIRED`, `APPROVAL_GRANTED` y
  `ORCHESTRATION_COMPLETED`.

### 4. Policy coverage

Anadir tests de policy si el flujo descubre huecos:

- el orchestrator puede asignar `reviewer`;
- `claude-code/reviewer` puede consumir `artifact.get.sanitized.raw_restricted`;
- `claude-code/reviewer` no puede leer raw restricted;
- `claude-code/reviewer` no puede escribir codigo.

No relajar el modelo para permitir raw restricted al reviewer.

### 5. Documentacion

Actualizar `docs/operator-guide.md` con el flujo minimo real por MCP. Debe quedar
claro que el `taskId` de `task.assign` se pasa a `agent.spawn` o
`agent.delegate`.

## Errores comunes

- Probar solo `tools/list` y no ejecutar `tools/call`.
- Usar `services.agent.spawn` directamente.
- Pasar raw restricted al reviewer como prompt.
- Crear una tarea reviewer sobre repo `restricted` con Claude.
- Tratar `approval.respond` como accion del orchestrator. La respuesta la da el
  operador o helper CLI.
