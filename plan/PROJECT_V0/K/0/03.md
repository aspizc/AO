# K/0/3 - Agent MCP runtime wiring

## Quick reference

| Campo | Valor |
|---|---|

| Branch | `feature/K-0-3-agent-mcp-runtime-wiring` |
| Depende de | K/0/2, I/0/2, O/0/2, P/0/0, R/0/1 |
| Esfuerzo | M (3-5h) |

## Por que existe?

El codigo tiene `AgentService`, adapters para Gemini/Claude y un adapter Codex
dormido, pero el Gateway MCP no expone `agent.delegate`, `agent.spawn`,
`agent.ask`, `agent.view` ni `agent.kill`. El operador no puede ejecutar el
flujo practico desde un LLM-orchestrator conectado por MCP aunque los servicios
internos y los E2E in-process pasen.

Esta tarea reabre Stage K para hacer real el contrato MCP que ya documentan el
system prompt y la guia de operador.

## Que hay que hacer?

Exponer las cinco tools `agent.*` por MCP, crear el `AgentService` real desde
`getToolRegistry`, registrar los adapters disponibles, cerrar el caso de sesion
sin `taskId`, y actualizar los smoke tests para que fallen si la superficie
`agent.*` desaparece.

## Pre-requisitos

- `gateway/src/services/agent_service.js` existe y aplica policy antes de
  llamar adapters.
- `GeminiAdapter`, `ClaudeAdapter` y `CodexAdapter` existen.
- Codex sigue `enabled: false` por defecto y debe fallar cerrado.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/K-0-3-agent-mcp-runtime-wiring
```

### 2. Tests rojos primero

Anadir o actualizar:

- `tests/gateway/tool_agent.test.js`
  - `mcp_agent_tools_are_registered`
  - `agent_spawn_requires_task_id`
  - `dry_run_spawn_ask_view_kill_cycle`
  - `disabled_codex_returns_structured_adapter_error`
- `tests/gateway/mcp_bootstrap.test.js`
  - `tools/list` debe incluir las cinco tools `agent.*`.
- `scripts/smoke_mcp.mjs`
  - el smoke debe exigir al menos `agent.spawn` y `agent.ask`, ademas de las
    tools core actuales.

Si K/0/1 o K/0/2 quedaron implementadas en otra rama, estos tests deben probar
la conducta real del codigo actual, no solo que existan archivos.

### 3. Crear `gateway/src/tools/agent.js`

Exponer:

- `agent.delegate`
- `agent.spawn`
- `agent.ask`
- `agent.view`
- `agent.kill`

Usar `defineTool` y esquemas Zod estrictos. Para evitar sesiones huerfanas:

- `agent.spawn` requiere `taskId`.
- `agent.delegate` requiere `taskId` si persiste una session row.
- Si se decide permitir `delegate` sin `taskId`, la respuesta debe declarar
  explicitamente `persisted: false` y no puede devolver un `sessionId` que luego
  parezca usable por `ask/view/kill`.

La ruta recomendada para MVP practico es exigir `taskId` en ambas llamadas de
ejecucion desde MCP.

### 4. Wirear adapters en `gateway/src/tools/index.js`

`getToolRegistry({ config, registries })` debe construir:

```text
createAdapterRegistry
  gemini-cli -> GeminiAdapter
  claude-code -> ClaudeAdapter
  codex -> CodexAdapter (registrado, pero disabled por policy/registry)
createAgentService
buildAgentTools
```

No duplicar policy en tools: la tool valida shape de input; el service y el
adapter mantienen policy-before-action.

### 5. Hook de intervencion tmux

Integrar el detector de R/0/1 en `agent.ask` / `agent.view`:

- registrar snapshot esperado antes/despues de `ask` cuando aplique;
- ejecutar `checkForIntervention` en `view` y despues de `ask`;
- auditar `HUMAN_TMUX_INTERVENTION` sin bloquear el flujo normal.

Si la integracion requiere pequenos ajustes al detector, mantenerlos dentro de
R/K y cubrirlos en tests.

### 6. Errores MCP estructurados

Las respuestas de error deben ser seguras para MCP:

```json
{ "error": "POLICY_DENIED|ADAPTER_DISABLED|ADAPTER_NOT_IMPLEMENTED|INVALID_INPUT|TOOL_ERROR", "message": "..." }
```

No devolver stack traces al cliente.

## Errores comunes

- No registrar adapters en el Gateway real y probar solo con servicios
  in-process.
- Devolver un `sessionId` no persistido cuando falta `taskId`.
- Habilitar Codex por defecto.
- Hacer que una llamada MCP de error cierre el servidor stdio.
- Escribir logs a stdout.
