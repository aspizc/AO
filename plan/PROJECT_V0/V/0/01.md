# V/0/1 - Propagar `model` por tools y agent service

## Quick reference

| Campo | Valor |

| Esfuerzo | M (3-5h) |
| Skills | MCP tools, services |

## Por que existe?

V/0/0 ensena al registry y a la policy que existen modelos, pero el orquestador
todavia no puede pedirlos: el tool schema de `agent.delegate` / `agent.spawn` no
acepta `model`, y `agent_service` no lo pasa al adapter. Esta tarea conecta el
parametro de punta a punta sin romper compatibilidad.

## Que hay que hacer?

Anadir `model` (opcional) a los schemas de `agent.delegate` y `agent.spawn`, y
`reasoningEffort` (opcional). En `agent_service`, resolver el modelo via la
policy (V/0/0), inyectar el resuelto en la llamada al adapter, y auditarlo. Los
adapters reciben `model`/`reasoningEffort` en su firma (los que no lo usen lo
ignoran de forma segura).

## Pre-requisitos

- V/0/0 mergeado: policy resuelve y valida modelos.
- `agent.*` tools expuestos por MCP (K/0/1).

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V-0-1-model-plumbing
```

### 2. Tool schemas

En `gateway/src/tools/agent.js`:

- `DelegateSchema` y `SpawnSchema`: anadir
  `model: z.string().optional()` y `reasoningEffort: z.string().optional()`.
- Actualizar `description` de ambos tools mencionando que `model` es opcional y
  cae al default del registry si se omite.

### 3. Agent service

En `gateway/src/services/agent_service.js`:

- En `delegate` y `spawn`, al llamar `assertAllowed`, pasar `model` y
  `reasoningEffort` en el contexto para que la policy los valide y resuelva
  (V/0/0).
- Tomar `model`/`reasoningEffort` **resueltos** desde la decision y pasarlos al
  adapter: `adapter.delegate({ ..., model, reasoningEffort })` y
  `adapter.spawn({ ..., model, reasoningEffort })`.
- Auditar el modelo efectivo en el evento (`auditServiceError` ya existe para
  errores; anadir `model` al flujo de exito si el adapter no lo audita ya).

### 4. Firmas de adapters

En `base_adapter.js` documentar que `delegate`/`spawn` reciben `model` y
`reasoningEffort` opcionales. Gemini y Codex (dry-run actual) deben **aceptar y
ignorar con seguridad** estos campos hasta que los implementen (V/0/2 para
Claude, W para Codex).

### 5. Tests

`tests/gateway/tool_agent_model.test.js`:

- `delegate_without_model_uses_default`.
- `delegate_with_allowed_model_passes_to_adapter` (spy sobre adapter).
- `delegate_with_disallowed_model_denied` (no llega al adapter).
- `spawn_passes_model_and_effort_to_adapter`.
- `reasoning_effort_only_applies_to_codex_context`.

Usar un adapter fake registrado para verificar que recibe el modelo resuelto.

## Errores comunes

- Validar el modelo en el tool en vez de en la policy (duplica logica).
- Pasar el `model` solicitado en bruto al adapter sin pasar por el resuelto.
- Romper Gemini al exigir `model`.
- No auditar el modelo efectivo (dificulta el trazado del MVP2.0).
