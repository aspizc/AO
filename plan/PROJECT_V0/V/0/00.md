# V/0/0 - Modelos permitidos en registry + policy

## Quick reference

| Campo | Valor |

| Esfuerzo | S-M (2-4h) |
| Skills | JSON registries, policy engine |

## Por que existe?

El MVP2.0 necesita pedir un modelo concreto por agente (`gpt-5 medium` para
Codex, `claude-opus-4-7` para Claude). Hoy `policies/agent-capabilities.json` no
declara modelos, asi que no hay forma deterministica de validar ni de elegir un
default. Esta tarea anade el vocabulario de modelos al registry y la regla de
policy que lo valida, **sin** tocar adapters todavia.

## Que hay que hacer?

Extender `agent-capabilities.json` con `models` (lista permitida) y
`defaultModel` por agente; para Codex anadir `reasoningEfforts` y
`defaultReasoningEffort`. Anadir al policy engine una comprobacion
`agent.model.allowed` que rechace un modelo fuera de la lista del agente, con
razon clara y decision auditable.

## Pre-requisitos

- Policy engine determinista de Stage C operativo.
- Registries cargados desde `policies/` (Stage B).

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V-0-0-model-registry-policy
```

### 2. Registry

Editar `policies/agent-capabilities.json`. Por agente anadir:

```jsonc
"claude-code": {
  "binary": "claude",
  "models": ["claude-opus-4-7", "claude-sonnet-4-6", "opus", "sonnet"],
  "defaultModel": "claude-opus-4-7",
  ...
},
"codex": {
  "binary": "codex",
  "models": ["gpt-5", "gpt-5-codex"],
  "defaultModel": "gpt-5",
  "reasoningEfforts": ["low", "medium", "high"],
  "defaultReasoningEffort": "medium",
  ...
},
"gemini-cli": {
  "binary": "gemini",
  "models": ["gemini-2.5-pro", "gemini-2.5-flash"],
  "defaultModel": "gemini-2.5-pro",
  ...
}
```

Subir `"version"` del registry. Los valores son una lista **local** y
versionada; no se consultan catalogos remotos.

### 3. Schema

Actualizar el JSON Schema de agent-capabilities (Stage B) para aceptar los
nuevos campos opcionales `models`, `defaultModel`, `reasoningEfforts`,
`defaultReasoningEffort`. Mantener compatibilidad: agentes sin `models` siguen
validando.

### 4. Policy

En el policy engine anadir resolucion de modelo:

- Helper `resolveModel(agentDef, requestedModel)`:
  - si `requestedModel` es null/undefined -> `agentDef.defaultModel`;
  - si esta en `agentDef.models` -> ese modelo;
  - en otro caso -> decision `deny` con `reason = "model <x> not allowed for agent <a>"`.
- Helper analogo `resolveReasoningEffort(agentDef, requested)` para Codex.
- La evaluacion de `agent.delegate` / `agent.spawn` debe poder recibir un
  `model` y `reasoningEffort` opcionales en el contexto y aplicarlos. La decision
  resultante incluye el `model`/`reasoningEffort` resueltos para que el caller
  los pase al adapter.

La validacion ocurre **antes** de cualquier spawn (coherente con ADR-003).

### 5. Tests

`tests/gateway/policy_model.test.js`:

- `default_model_used_when_omitted`.
- `allowed_model_resolves_ok` (`gpt-5`, `claude-opus-4-7`).
- `disallowed_model_denied_with_reason`.
- `codex_default_reasoning_effort_is_medium`.
- `disallowed_reasoning_effort_denied`.
- `agent_without_models_block_keeps_validating` (compat).

## Errores comunes

- Hacer `model` obligatorio y romper Gemini/Claude existentes.
- Validar el modelo despues del spawn (viola ADR-003).
- Hardcodear modelos en el engine en vez de leerlos del registry.
- Olvidar versionar el bump del registry.
