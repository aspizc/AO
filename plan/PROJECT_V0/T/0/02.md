## ¿Por que existe?

Un operador nuevo (humano o agente) tiene que poder ir de cero a un dry-run sin abrir codigo del Gateway. Necesita una guia paso-a-paso **host-agnostica**: instala deps, valida policy, lanza Gateway desde cualquier MCP host, ejecuta E2E dry-run, lee audit.

## ¿Que hay que hacer?

`docs/operator-guide.md` con secciones de instalacion, validacion, primer dry-run, troubleshooting.

### 2. `docs/operator-guide.md`

```markdown
# Operator guide

This guide takes a fresh operator from clone to a successful local
dry-run. It is **host-agnostic**: it does not assume Cursor, Antigravity
or any specific MCP IDE.

## 1. Prerequisites

- Linux, macOS or WSL.
- Node 20+ (`node --version`).
- Python 3.11+ (`python3 --version`).
- tmux (only required for supervised mode).

## 2. Clone and install

```bash
git clone <this repo>
cd agents-orchestrator
python3 -m venv .venv
source .venv/bin/activate
pip install -e "cli[dev]"
npm --prefix gateway install
```

## 3. Validate registries

```bash
agent-run policy validate
```

Should print `OK policies dir: ...`. If you see `FAIL`, fix the
`policies/*.json` file mentioned and rerun.

## 4. Run local CI

```bash
./scripts/ci.sh
```

All checks must pass before going further.

## 5. Launch the Gateway from any MCP-capable host

The Gateway speaks MCP over stdio. Configure your host to spawn
`node ./gateway/src/mcp_server.js` as an MCP server named
`agents-gateway`. See [`../client-config/mcp.json.example`](../client-config/mcp.json.example)
for the generic example.

> Adapting this example to a specific IDE (Cursor, Antigravity, etc.)
> is **out of scope** for this project. You'll need to translate the
> generic config to your host's format.

## 6. Inject the orchestrator system prompt

When you instruct your LLM client to act as the orchestrator role,
load [`../prompts/orchestrator_system_prompt.md`](../prompts/orchestrator_system_prompt.md)
as the system prompt or equivalent.

## 7. Run your first dry-run orchestration

Set `AGENTS_DRY_RUN=1` in the env passed to the Gateway. From any
MCP client, call:

```text
orchestration.create  { callerAgent: "claude-code", callerRole: "orchestrator", goal: "Refactor X" }
task.assign          { traceId: <returned>, caller: {...}, target: { role: "restricted-coder" }, repo: "cvision" }
agent.spawn          { agent: "gemini-cli", role: "restricted-coder", repo: "cvision", cwd: "<allowed path>", traceId: <returned>, taskId: <returned> }
```

The Gateway will return mock responses. Inspect the audit:

```bash
agent-run audit show --trace-id <traceId> --limit 50
```

You should see `ORCHESTRATION_CREATED`, `TASK_CREATED`, `SESSION_STARTED`,
`SESSION_CLOSED`.

## 8. Approvals (operator side)

When the orchestrator requests an approval, the audit shows
`APPROVAL_REQUIRED`. To respond from terminal:

```bash
agent-run approve <approvalId> --decision granted --note "release plan reviewed"
agent-run approve <approvalId> --decision denied  --note "do not push yet"
```

## 9. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| MCP host says "no tools" | Gateway crashed at boot. Check stderr. | Re-run with `AGENTS_DRY_RUN=1` and tail stderr from the host. |
| `tools/list` works but tools fail | Policy denying. | Run `agent-run policy check` with the same context. |
| stdout looks corrupted | Some code logged to stdout instead of stderr. | Open a bug; the Gateway must keep stdout for MCP only. |

## Out of scope

- Cursor, Antigravity IDE and any specific IDE configuration.
- Network deployment, multi-user auth, cloud hosting.
- Automatic approval (the human operator is the authority).
```
