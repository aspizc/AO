## Por que existe?

En el flujo MVP2.0 (coder Codex + reviewer Claude) el humano acepta los cambios
del coder antes de darlos por buenos. El operador quiere poder dejar correr ese
flujo de forma autonoma, igual que en planificacion (Z/0/4). El mecanismo de
auto-approval ya existe (Q/0/5); esta tarea **define la puerta `code.apply`** del
flujo coder+reviewer y la **suscribe** al scope autonomo.

> Aplica al coder y al reviewer el mismo principio que Z/0/4 aplica al planner.

## Que hay que hacer?

Definir que la aceptacion de los cambios del coder (tras el review) se solicita
con `action: "code.apply"`, documentar que `AGENTS_AUTOAPPROVE=code.apply` activa
el modo autonomo de este flujo, y ajustar el system prompt del orquestador y el
runbook MVP2.0. El comportamiento por defecto (humano acepta) no cambia.

## Pre-requisitos

- Q/0/5 mergeado (mecanismo + `AGENTS_AUTOAPPROVE`).
- X/0/1 (system prompt de 2 agentes) y X/0/2 (runbook) mergeados.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/Y-0-3-code-autoapprove-scope
```

### 2. Puerta `code.apply`

En `prompts/orchestrator_mvp2_two_agent.md` (X/0/1): tras el review del reviewer,
el orquestador solicita
`approval.request({ action: "code.apply", context: { repo, agent: "codex", role: "coder" } })`
y espera con `approval.wait` antes de dar por aceptados los cambios. Si el
operador habilito el scope, Q/0/5 lo auto-concede; si no, espera al humano.

Distinguir claramente de las acciones peligrosas que **nunca** se auto-conceden
(`git.push.protected`, `dependency.change`, `code.write.protected_branch`): esas
siguen requiriendo humano aunque `code.apply` este en modo autonomo.

### 3. Modo autonomo (documentar)

- `AGENTS_AUTOAPPROVE=code.apply` activa el modo (operador, al lanzar). Se puede
  combinar: `AGENTS_AUTOAPPROVE=plan.apply,code.apply`.
- Seccion **Autonomous mode** en el system prompt:
  - el flujo no pausa en `code.apply`;
  - el **reviewer sigue revisando** y registrando `review_notes`; un veredicto KO
    del reviewer detiene el flujo aunque el modo este activo (no se auto-acepta
    trabajo que el propio reviewer rechaza);
  - trabajo en rama; nunca push autonomo.

### 4. Perfil y runbook

- `client-config/profiles/codex-coder-claude-reviewer/.env.example`: documentar
  `AGENTS_AUTOAPPROVE` (default vacio; ejemplo `code.apply`).
- `docs/mvp2-orchestrator-runbook.md`: seccion "Modo autonomo": como activarlo,
  que auto-concede (`code.apply`) y que no, como auditar (`APPROVAL_AUTO_GRANTED`).

### 5. Tests

`tests/gateway/code_autoapprove_scope.test.js`:

- `code_apply_pending_when_scope_absent`.
- `code_apply_auto_granted_when_scope_present` (audit).
- `code_apply_never_grants_protected_push_even_with_scope`.
- `restricted_repo_code_apply_never_auto_granted`.
