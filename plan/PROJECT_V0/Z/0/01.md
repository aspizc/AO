## Por que existe?

El bucle draft -> apply -> review -> escalate necesita instrucciones precisas
para cada rol: como redacta y revisa el planner, como aplica el coder sin inventar
alcance, y como se escalan al humano las decisiones mal definidas. Sin esto, el
host no ejecuta el bucle de forma consistente ni segura.

## Que hay que hacer?

Escribir tres piezas de prompt: (a) system prompt del **planner** (draft+review),
(b) instrucciones del **coder de aplicacion**, y (c) un addendum para el
**orquestador** que describe el bucle y el manejo de "decisiones abiertas". Definir
un formato explicito de seccion `OPEN DECISIONS / QUESTIONS FOR HUMAN`.

## Pre-requisitos

- Z/0/0 mergeado (planner puede review_notes; repo registrado).
- Conocer el formato de tarea de `plan/PROJECT_V0/README.md` y las convenciones globales.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/Z-0-1-planner-loop-prompts
```

### 2. Planner prompt

`prompts/planner_system_prompt.md`:

- **Rol**: redactas y refinas planes en el formato `plan/PROJECT_V0/<stage>/<task>.md`
  (Quick reference, Por que existe, pasos, archivos, tests, criterios, DoD).
- **Draft con el humano**: propones estructura y tareas; haces preguntas concretas;
  no asumes alcance no confirmado.
- **Review del coder**: tras la fase apply, recuperas el diff del coder
  (`artifact.get.sanitized`) y lo comparas con el plan acordado; registras
  correcciones precisas via `artifact.put.review_notes` (que fichero, que linea,
  que cambia y por que).
- **Escalado**: toda ambiguedad o decision no cerrada va en una seccion
  `## OPEN DECISIONS / QUESTIONS FOR HUMAN` con: id, contexto, opciones y tu
  recomendacion. No la resuelves tu si afecta alcance o seguridad.
- **Limites**: no escribes ficheros (no tienes `code.write`); no spawneas agentes;
  la policy del gateway es la autoridad.

### 3. Coder (apply) prompt

`prompts/planner_apply_coder_prompt.md` (o `--append-system-prompt`):

- Aplicas **exactamente** el plan aprobado a `plan/*.md`. No inventas tareas ni
  cambias alcance.
- **Solo** tocas `plan/**`. Nunca `policies/`, `gateway/`, `tests/`, ni codigo.
- Donde el plan tenga una `OPEN DECISION` sin resolver, dejas un marcador
  `<!-- TODO(open-decision:<id>): pendiente de humano -->` en vez de inventar.
- No haces `git push` ni commits sin aprobacion del operador.

### 4. Orquestador addendum

`prompts/orchestrator_planning_loop.md`:

- Secuencia: `task.assign` planner -> `agent.spawn`/`ask` planner (draft) ->
  presentar al humano y recoger respuestas a `OPEN DECISIONS` -> `agent.spawn`/`ask`
  coder (apply) -> `agent.spawn`/`ask` planner (review) -> aplicar correcciones ->
  repetir hasta aprobacion -> `approval.request` final -> `orchestration.complete`.
- El orquestador es quien **traslada al humano** las `OPEN DECISIONS` (in-band) y
  usa `approval.request`/`approval.wait` para la puerta de aplicacion.
- Recordatorio de seguridad: edits scoped a `plan/**`, revision por `git diff`,
  trabajo en rama.

### 5. Enlazar

Referenciar los tres desde el perfil (Z/0/2) y el runbook (Z/0/3).

## Errores comunes

- Que el planner "decida" ambiguedades de alcance en vez de escalarlas.
- Que el coder toque ficheros fuera de `plan/**`.
- Olvidar el formato `OPEN DECISIONS` (rompe el escalado al humano).
- Hacer del prompt la frontera de seguridad (lo es la policy).

## Verificacion manual

Lectura cruzada con `policies/roles.json`: cada accion citada esta permitida para
su rol. Ensayo en dry-run con el perfil de Z/0/2: el host intenta la secuencia y
produce un artefacto de plan con seccion `OPEN DECISIONS`.

## Criterios de aceptacion
