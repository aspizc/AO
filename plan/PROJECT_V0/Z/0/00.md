## Por que existe?

El bucle de planificacion necesita dos cosas que hoy no existen:

1. El rol `planner` solo puede `artifact.put.plan`; para **revisar y corregir** lo
   que el coder aplica, necesita registrar correcciones
   (`artifact.put.review_notes`).
2. Este repo (`agents-orchestrator`) **no esta en** `repositories.json`, asi que
   un coder claude-code no puede escribir `plan/*.md` aqui (policy lo deniega por
   repo desconocido).

Esta tarea habilita ambas cosas con el minimo cambio de policy, manteniendo las
prohibiciones duras (planner sin `code.write` ni `agent.spawn`).

## Que hay que hacer?

Anadir `artifact.put.review_notes` a `planner.allowActions`; registrar
`agents-orchestrator` como repo `internal` con `claude-code` permitido; y dejar
claro (tests) que el planner sigue sin poder escribir codigo ni spawnear.

## Pre-requisitos

- V/0/0 mergeado (modelos en registry).
- Entender `policies/roles.json` y `policies/repositories.json` y como
  `policy_engine` resuelve `repo` + `role` + `action`.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/Z-0-0-planner-review-contract
```

### 2. Rol planner

En `policies/roles.json`, `planner.allowActions` -> anadir
`"artifact.put.review_notes"`. Mantener `denyActions` con `code.write` y
`agent.spawn`. Resultado:

```jsonc
"planner": {
  "purpose": "Draft and refine plans, and review plan changes applied by a coder.",
  "allowActions": ["artifact.put.plan", "artifact.put.review_notes",
    "artifact.get.sanitized", "policy.check"],
  "denyActions": ["code.write", "agent.spawn"]
}
```

### 3. Registrar este repo

En `policies/repositories.json` anadir:

```jsonc
"agents-orchestrator": {
  "classification": "internal",
  "allowedAgents": ["gemini-cli", "claude-code"],
  "tags": ["self", "planning"]
}
```

`internal` permite `code.write` al rol `coder` con claude-code (que admite
`internal`). No se anade Codex aqui (el bucle usa claude-code).

### 4. Subir versiones

Bump `version` de `roles.json` y `repositories.json`.

### 4b. ADR + threat-model (obligatorio)

Registrar este repo como escribible por un coder es una decision de scope nueva
respecto a ADR-004/005; documentarla:

- `docs/adr/ADR-007-planner-assisted-self-planning.md`: el sistema puede operar
  sobre su **propio** repo (`agents-orchestrator`, `internal`) para refinar
  `plan/*.md` mediante el bucle planner+coder; el coder solo debe tocar `plan/**`;
  garantias = aprobacion humana (salvo modo autonomo Z/0/4), trabajo en rama,
  revision por `git diff`; el planner no escribe. Extiende ADR-005.
- `docs/threat-model.md` — anadir **TM-13 (Self-repo modification via planning
  coder)**: vector = el coder del bucle edita `policies/` o `gateway/` para
  escalar privilegios en vez de solo `plan/**`; control = prompt acota a `plan/**`,
  aprobacion humana + `git diff`, rama dedicada, y (recomendado) revision del
  planner del diff antes de aceptar; `Tested by:` cobertura en la suite de bypass.

## Errores comunes

- Dar `code.write` al planner (rompe la separacion del bucle).
- Clasificar este repo como `unrestricted` sin pensar (es tooling: `internal`).
- Anadir Codex a `agents-orchestrator` (no participa en el bucle de planning).
- Tocar la clasificacion de repos restricted.
