## Por que existe?

El host MCP necesita instrucciones concretas para ejecutar el flujo de 2 agentes
supervisados del MVP2.0. El prompt base (`prompts/orchestrator_system_prompt.md`,
T/0/1) es generico. Esta tarea anade un prompt especifico que cablea coder Codex
(gpt-5 medium) + reviewer Claude (opus-4.7) en sesiones tmux, respetando policy,
sanitizacion y approvals.

## Que hay que hacer?

Crear `prompts/orchestrator_mvp2_two_agent.md`: un system prompt que el operador
pega en su host. Describe el objetivo, los 2 agentes/roles/modelos, la secuencia
de tools `agent.spawn`/`ask`/`view`, el uso de artefactos sanitizados para el
reviewer, approvals async, y como cerrar la orquestacion.

### 2. Contenido del prompt

`prompts/orchestrator_mvp2_two_agent.md` debe cubrir:

- **Rol**: eres el orquestador; no escribes codigo ni accedes a raw restricted;
  coordinas via `agents-gateway`.
- **Agentes del flujo**:
  - coder = `agent: codex`, `role: coder`, `model: gpt-5`, `reasoningEffort: medium`;
  - reviewer = `agent: claude-code`, `role: reviewer`, `model: claude-opus-4-7`.
- **Secuencia recomendada**:
  1. `orchestration.create` + `task.assign` al coder.
  2. `agent.spawn` del coder (tmux); `agent.ask` con la tarea; `agent.view` para
     seguir el progreso.
  3. El coder produce un artefacto; el orquestador lo comparte **sanitizado** con
     el reviewer (`artifact.share` / `artifact.get.sanitized`).
  4. `agent.spawn` del reviewer; `agent.ask` para revisar el diff/resumen
     sanitizado; recoge `artifact.put.review_notes`.
  5. Si se requiere approval (p.ej. push a protected), `approval.request` +
     `approval.wait` (async, no bloquea).
  6. `agent.kill` de ambas sesiones; `orchestration.complete`.
- **Reglas duras**: el reviewer nunca ve raw restricted; Codex prohibido en
  `restricted`; usar `policy.check` ante la duda; la policy del gateway es la
  autoridad, no este prompt.
- **Intervencion humana**: el operador puede `tmux attach` a una sesion; usar
  `session.attach_info` y `session.intervention_note`.

## Errores comunes

- Hacer del prompt la frontera de seguridad (la policy lo es).
- Permitir que el reviewer pida artefactos raw.
- Saltarse la sanitizacion entre coder y reviewer.
- Bloquear en approvals sincronos (deben ser async).

## Verificacion manual

Lectura cruzada con `policies/roles.json`: cada accion mencionada esta permitida
para el rol que la ejecuta. Pegar el prompt en un host con el perfil dry-run y
comprobar que el host intenta la secuencia correcta.
