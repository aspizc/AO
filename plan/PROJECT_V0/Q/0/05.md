# Q/0/5 - Auto-approval acotada opt-in (mecanismo compartido)

## Quick reference

| Campo | Valor |
|---|---|
| Stage | Q - Approval workflow async |
| Branch | `feature/Q-0-5-bounded-autoapprove` |
| Depende de | Q/0/1, Q/0/2 |
| Esfuerzo | M (3-5h) |
| Skills | approvals, config, audit, ADR |

## Por que existe?

El MVP1 prohibio toda aprobacion automatica ("el humano es la autoridad"). La
practica pide poder dejar correr ciertos flujos de forma autonoma (planificacion
y coder+reviewer) sin revisar cada diff. Esta tarea **evoluciona ese invariante**
introduciendo un mecanismo **opt-in, acotado y auditado**: el humano sigue siendo
la autoridad por defecto y **siempre** para operaciones peligrosas.

Es la **capacidad compartida** sobre la que se apoyan Z/0/4 (scope `plan.apply`) e
Y/0/3 (scope `code.apply`). Se implementa una sola vez aqui.

## Que hay que hacer?

Anadir al approval service un camino de **auto-grant** que se activa solo si el
**operador** lo habilito al lanzar, limitado a una allowlist de scopes y con un
conjunto inmutable de acciones que **nunca** se auto-conceden. Auditar cada
auto-grant. El orquestador no puede ni activarlo ni responder approvals.

## Pre-requisitos

- Q/0/1 (service) y Q/0/2 (tools) mergeados.
- `orchestrator.denyActions` incluye `approval.respond` (no se toca).

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/Q-0-5-bounded-autoapprove
```

### 2. Config (gate del operador)

En `gateway/src/config.js`:

| Env var | Default | Descripcion |
|---|---|---|
| `AGENTS_AUTOAPPROVE` | `""` | Lista separada por comas de scopes auto-concedibles. Vacio = off. |

`config.autoApproveScopes = (env.AGENTS_AUTOAPPROVE || "").split(",").map(s=>s.trim()).filter(Boolean)`.

### 3. Conjuntos de control

En `gateway/src/services/approval_service.js`:

```js
// Nunca auto-concedibles, aunque se listen en AGENTS_AUTOAPPROVE.
const NEVER_AUTO = new Set([
  "git.push.protected",
  "dependency.change",
  "code.write.protected_branch",
]);
```

Un scope solo es auto-concedible si: esta en `config.autoApproveScopes`, **no**
esta en `NEVER_AUTO`, y el `context` no indica clasificacion `restricted`.

### 4. Auto-grant en `request`

`request({ traceId, action, requestedBy, context })`:

- Si `isAutoApprovable(action, context, config)`:
  - crear la aprobacion ya `granted` (no `pending`);
  - audit `APPROVAL_AUTO_GRANTED` con `decidedBy: "operator-autonomous-mode"`,
    `action`, `scope`, `traceId`;
  - emitir en `approvalBus` para que `approval.wait` resuelva de inmediato;
  - retornar `{ approvalId, status: "granted", auto: true }`.
- En cualquier otro caso, comportamiento actual (`pending` + espera humana).

`config` debe inyectarse al servicio (hoy `request` no lo recibe): via el builder
de tools / init de servicio. Sin estado global oculto.

### 5. ADR

`docs/adr/ADR-006-bounded-autoapprove.md`: documenta que el invariante "sin
aprobacion automatica" del MVP1 se relaja a "auto-approval **opt-in, acotada y
auditada**"; el humano sigue siendo autoridad por defecto y siempre para
`NEVER_AUTO` y repos `restricted`; el orquestador no puede activarla. Nota: alinea
con la "autonomia por defecto dentro del scope" ya descrita en
`plan_proyecto_v4.md`.

### 5b. Reconciliar documentacion existente (obligatorio)

Este cambio contradice afirmaciones del MVP1; actualizarlas en el mismo PR:

- `docs/operator-guide.md` — la linea "Out of scope: Automatic approval. The
  human operator remains the authority." pasa a: auto-approval **opt-in** acotada
  existe (ver ADR-006); el humano es autoridad por defecto y siempre para
  operaciones peligrosas; documentar `AGENTS_AUTOAPPROVE` en la seccion de
  approvals.
- `docs/threat-model.md` — anadir **TM-12 (Auto-approval abuse / over-broad
  enablement)**: vector = operador habilita scopes de mas o el orquestador induce
  approvals repetidos; control = `NEVER_AUTO` inmutable, gate solo de operador,
  `restricted` excluido, audit `APPROVAL_AUTO_GRANTED`, orquestador no responde;
  `Tested by:` el test nuevo + una entrada en `tests/e2e/bypass_regression.test.js`
  (el threat-model exige cobertura en la suite de bypass).
- `README.md` — seccion Scope/architecture: mencionar auto-approval opt-in
  (default off) como capacidad.

## Errores comunes

- Hacer el modo el default o global sin scopes.
- Permitir que el orquestador lo active o responda approvals.
- Auto-conceder algo de `NEVER_AUTO` o en repos `restricted`.
- Auto-grant sin evento de audit distinguible.
