## ¿Por que esta tarea existe?

Pasada la frontera de clasificacion, el siguiente filtro es el rol. Aqui se cierra TM-01 (prompt injection contra el orchestrator-LLM): aunque el orchestrator pidiera `code.write`, el motor lo rechaza por rol. Tambien aqui se valida `task.assign`: el caller orchestrator + el target {agent, role} deben ser ambos legales.

## ¿Que hay que hacer?

Anadir al `policy_engine.js` la capa de validacion de rol: ¿el agente puede asumir ese rol? ¿La accion esta en `denyActions` del rol? Caso especial `task.assign`: chequear caller (orchestrator) Y target (recursivo).

### 2. Extender `policy_engine.js`

```javascript
function actionMatchesDeny(action, deny) {
  return deny.includes(action) || deny.some((d) => action.startsWith(d + "."));
}

function evaluateRole(ctx, registries) {
  const agent = registries.getAgent(ctx.agent);
  if (!agent.allowedRoles.includes(ctx.role)) {
    return deny(`agent ${ctx.agent} cannot assume role ${ctx.role}`,
                "role.agent_not_allowed_for_role");
  }
  const role = registries.getRole(ctx.role);
  if (!role) return deny(`unknown role ${ctx.role}`, "role.unknown");

  if (Array.isArray(role.denyActions) && actionMatchesDeny(ctx.action, role.denyActions)) {
    return deny(`role ${ctx.role} denies action ${ctx.action}`, "role.deny_action");
  }

  if (ctx.action === "task.assign") {
    if (ctx.role !== "orchestrator") {
      return deny("task.assign is restricted to orchestrator role", "role.task_assign_only_orchestrator");
    }
    if (!ctx.targetAgent || !ctx.targetRole) {
      return deny("task.assign requires targetAgent and targetRole", "role.task_assign_missing_target");
    }
    const targetAgent = registries.getAgent(ctx.targetAgent);
    const targetRole = registries.getRole(ctx.targetRole);
    if (!targetAgent || !targetRole) {
      return deny("task.assign target unknown", "role.task_assign_unknown_target");
    }
    if (!targetAgent.allowedRoles.includes(ctx.targetRole)) {
      return deny(`target agent ${ctx.targetAgent} cannot assume ${ctx.targetRole}`,
                  "role.task_assign_target_role_not_allowed");
    }
  }

  return null; // null means "this layer is happy, continue to next layer"
}

// Adjust evaluate() to call evaluateClassification first, then evaluateRole, etc.
```

Reorganiza `evaluate(...)`:

```javascript
export function evaluate(rawCtx, registries) {
  const ctx = normalizePolicyContext(rawCtx);

  const layers = [
    () => evaluateClassification(ctx, registries),
    () => evaluateRole(ctx, registries),
    // C/0/3 will add evaluateApproval
    // C/0/4 will add evaluateSanitization
  ];

  for (const layer of layers) {
    const r = layer();
    if (r && r.decision === Decision.DENY) return r;
    if (r && r.decision === Decision.REQUIRE_APPROVAL) return r;
    if (r && r.decision === Decision.ALLOW_WITH_SANITIZATION) return r;
    // ALLOW or null → continue
  }
  return allow("all layers passed", "ok");
}
```

> El existing test `gemini_allowed_on_restricted` pasaba al ALLOW de classification. Ahora ese ALLOW se considera "ok layer", y el siguiente layer (role) tiene la palabra final.

## Errores comunes a evitar

- ❌ Hacer del rol orchestrator un caso especial con privilegios extra. **Es lo opuesto**: el orchestrator es el rol con MAS denegaciones explicitas.
- ❌ Olvidar validar el target en `task.assign`. Si no lo haces, la orchestracion entera se vuelve un bypass.
- ❌ Permitir `task.assign` desde otro rol (e.g. coder) "por simplicidad". Solo `orchestrator`.

## Criterios de aceptacion

- [ ] `orchestrator` no escribe codigo ni lee raw restricted.
- [ ] `orchestrator` puede delegar a target valido.
- [ ] `task.assign` desde otro rol → deny.
- [ ] `task.assign` con target invalido → deny.
