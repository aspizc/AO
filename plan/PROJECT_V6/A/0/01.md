## Problem

A Claude Code plugin (hook, skill, status line) loaded inside a Gateway child
cannot tell that it is a worker rather than the human-facing orchestrator, so
orchestrator-only behaviour (spawning reviewers, committing, paging the human)
can fire inside workers.

Current env forwarding:

- Headless delegates call `spawnSync` with no `env` (inherit the Gateway's
  `process.env`): `claude_adapter.js:238`, `codex_adapter.js:284`,
  `antigravity_adapter.js:238`. Only pi and opencode
  pass an `env`, built by `childEnv` to add `OLLAMA_BASE_URL`/`OLLAMA_HOST` from
  `AGENTS_OLLAMA_BASE_URL` (`pi_adapter.js:60-64,257`,
  `opencode_adapter.js:72-76,269`, key at `model_credentials.js:14`).
- Supervised spawns run `tmux new-session -d -s <target> -c <cwd>`
  (`tmux_client.js:11-13`) and type the launch command into that shell
  (`claude_adapter.js:344-345` and the same pattern in each adapter). The child
  inherits the **tmux server's** environment, not the Gateway's, so nothing set
  in the Gateway process reaches it. (Observed side effect: pi/opencode
  `childEnv` is also not applied on spawn — see open question in the project
  reply; not fixed here.)
- `AGENTS_TRACE_ID` is already used by LangGraph to label the **Gateway**
  subprocess (`orchestrator-langgraph/src/orchestrator_langgraph/client/gateway_client.py:75`);
  a child inheriting `process.env` would see the parent's trace under that name.

## Scope

1. **Contract** (new `docs/worker-environment.md`, linked from
   `gateway/README.md`): every child the Gateway launches through
   `agent.delegate` or `agent.spawn` has exactly these variables set:

   | Variable | Value | Notes |
   |---|---|---|
   | `AGENTS_WORKER_ROLE` | resolved role of the child (e.g. `reviewer`) | presence = "I am a Gateway worker" |
   | `AGENTS_WORKER_TRACE_ID` | orchestration trace id of the child | distinct from `AGENTS_TRACE_ID` (Gateway's own label) |
   | `AGENTS_WORKER_TASK_ID` | bound task id, or empty string when none | always set, so a stale inherited value cannot survive |

   The marker is **informational, never authority**: any process can forge it;
   plugins may use it only to suppress orchestrator behaviour, never to unlock
   anything. Absence means "not launched by this Gateway", not "orchestrator".
2. Values come from the server-owned execution binding (`execution.role`,
   `execution.traceId`, `execution.taskId` in `agent_service.js`) / the
   adapter's own `role`, `traceId`, `taskId` arguments — never from prompt text.
   Reject (existing invalid-selection error) a value containing a newline or
   NUL.
3. Headless: each adapter passes
   `env: { ...base, ...workerEnv({ role, traceId, taskId }) }`, where `base` is
   `process.env` (or `childEnv(...)` for pi/opencode). Explicit values override
   any inherited `AGENTS_WORKER_*`.
4. Supervised: `buildNewSessionCmd({ target, cwd, env })` adds one
   `-e KEY=VALUE` per marker variable (argv, no shell; tmux ≥ 3.0, installed
   3.6). All five executable adapters pass it.
5. One shared helper `workerEnv` in `gateway/src/adapters/base_adapter.js` (all
   adapters already import from it or `tmux_client.js`); no per-adapter copy.
6. **Scope is the five executable providers** — `codex`, `claude-code`,
   `antigravity`, `pi`, `opencode`. `gemini-cli` is registry-only and refused
   before any session starts (see A/0/00 Problem); it is not touched and its
   refusal tests stay unchanged.
7. **Spawn result field `newSessionArgv`.** The marker travels on
   `tmux new-session`, not in the CLI `launchCommand`, and the service accepts
   only the exact spawn keys in `SPAWN_RESULT_FIELDS`
   (`gateway/src/services/agent_service.js:263-270`, enforced by
   `hasExactFields` in `assertAdapterSelectionResult`, `:431-450`, on the
   spawn path at `:663-668`). Each executable adapter's supervised spawn returns
   `newSessionArgv`: the exact frozen string array passed to `tmuxSync` for
   `new-session` (dry-run and live alike). `agent_service.js` adds
   `newSessionArgv` to `SPAWN_RESULT_FIELDS` (the list A/0/00 already extends
   with `writeAccess`) and validates it: a plain array of strings, first
   element `new-session`, containing `-s <tmuxTarget>` equal to the result's
   `tmuxTarget`, and exactly one `-e` pair for each of the three marker
   variables whose values equal the server-owned role, trace, and task (empty
   string when no task). Anything else is rejected with the existing
   invalid-selection error; selection-identity checks are unchanged.

## Non-scope

- Forwarding `AGENTS_OLLAMA_BASE_URL`/`OLLAMA_*` to supervised pi/opencode
  sessions (separate defect; see open questions).
- Stripping other inherited `AGENTS_*` Gateway configuration from children.
- Any authority, policy, or audit decision based on the marker.
- Shipping the consuming Claude Code plugin.
- Executable `gemini-cli` support.

## TDD RED

`tests/gateway/worker_env.test.js` plus extensions of `tmux_client.test.js` and
the adapter suites; each fails on current `HEAD`:

- `buildNewSessionCmd emits -e for each marker` (pure argv assertion).
- `delegate child env carries role/trace/task` — for each of the five
  executable adapters, stub
  `spawnSync` (or use a fake binary that prints `env`) and assert the three
  values; a reviewer under trace `tr-a`/task `tk-a` must not see the
  Gateway's `AGENTS_WORKER_*` or `AGENTS_TRACE_ID` value.
- `task-less delegate exports empty AGENTS_WORKER_TASK_ID` even when the
  Gateway env has `AGENTS_WORKER_TASK_ID=stale`.
- `pi/opencode keep OLLAMA_* alongside the marker`.
- `newline in a marker value is rejected`.
- `dry-run spawn returns newSessionArgv with the marker` for each of the five
  executable adapters (adapter-level, asserted on emitted output, not a
  fixture).
- Service level (new `tests/gateway/agent_service_worker_env.test.js`, through
  `createAgentService` (`agent_service.js:509`) dry-run spawn):
  `marker-bearing spawn result is accepted and returned with newSessionArgv`;
  rejects `newSessionArgv` that is not an array of strings, whose `-s` target
  differs from `tmuxTarget`, that lacks a marker `-e` pair, or whose marker
  value differs from the server-owned role/trace/task; rejects a spawn result
  without `newSessionArgv`.
- `gemini_delegate.test.js` / `gemini_supervised.test.js` run unchanged.

## TDD GREEN

Add `workerEnv`, the `env` parameter on `buildNewSessionCmd`, and the `env`
option on every executable adapter's `spawnSync`; return `newSessionArgv` from
each executable adapter's spawn; in `gateway/src/services/agent_service.js`
add `newSessionArgv` to `SPAWN_RESULT_FIELDS` and its validation (Scope 7);
thread `taskId` where an adapter does not yet receive it on spawn; write `docs/worker-environment.md` with a minimal
plugin-side check (`[ -n "$AGENTS_WORKER_ROLE" ]`).
