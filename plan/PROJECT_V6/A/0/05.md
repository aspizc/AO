## Problem

At verified base `327043a50316f3918b06fe30e019ecdc5799b4d3`,
`createGatewayRequestContext` (`gateway/src/core/request_context.js:918`)
seeds no lineage, `seedLineage` (`:146`) starts empty, and each MCP server
start draws a fresh connection ID (`gateway/src/mcp_server.js:244`). Earlier
traces fail `ownedTrace` (`request_context.js:405-410`), leaving surviving
tmux children unreachable through `agent.ask`, `agent.view` and `agent.kill`.

The production principal is the constant `local-stdio-operator`
(`request_context.js:933`); `loadConfig` supplies a provider identity but no
user principal (`gateway/src/config.js:203`). Traces start repository-free
(`request_context.js:447`, `:815`), while each task has its own verified
repository (`:458-475`, `:821-827`). Equality of a configured principal string
or one task's repository is therefore insufficient for restart recovery.

## Scope

### 1. Supported local identity

Recovery supports **Linux local stdio with the existing SQLite state DB**.
Read the process's numeric real and effective UIDs from the OS at startup;
both must be nonnegative safe integers and equal. The recovery principal is
`linux-uid:<uid>`; provider agent and role remain separate actor fields.
Derive this identity in the actual `mcp_server.js` bootstrap, independently
of caller fields, `requestPrincipalId`, provider names, `USER`/`LOGNAME`, or
other configured identity assertions. Re-read credentials before recovery
and refuse if they differ from startup. No credential-changing operation is
introduced. The trusted principal is the account running the stdio server,
not an authenticated remote user.

Bind that principal to a machine digest and the canonical SQLite DB path.
Read `/etc/machine-id` through a bounded, root-owned regular-file read
(open without following symlinks, validate that same descriptor with fstat);
refuse group/other-writable, absent, unreadable, empty, malformed or all-zero
values. Require exactly 32 lowercase hexadecimal characters plus an optional
final newline. Persist only HMAC-SHA256 of those 16 decoded bytes under the
fixed application key `agents-gateway/local-reattach/v1`, never the raw ID.
Resolve the existing `stateDb` file with realpath after `initState`; the DB
file and its directory must belong to the effective UID and be unwritable
by group/others for recovery. No chmod or ownership change is automatic.
A DB copied to a different machine digest or canonical path is refused even
when the numeric UID and registry IDs match.

This boundary assumes the local account, OS credential namespace, machine
identity and private state storage are trusted. Cloned machine identities,
root impersonation, shared/container UID namespaces and remote identity are
not cross-host authentication guarantees. Darwin, other platforms, missing
verified identity and PostgreSQL recovery are unsupported and fail closed:
`orchestration.reattach` returns the generic context denial and discovery
returns no entries. Existing non-recovery calls retain their current behavior;
unsupported identity must not prevent Gateway startup or normal calls.

The OS APIs and machine-ID format/privacy rules are documented by
[Node's process API](https://raw.githubusercontent.com/nodejs/node/v22.x/doc/api/process.md)
and [systemd's machine-ID specification](https://raw.githubusercontent.com/systemd/systemd/main/man/machine-id.xml).
The Linux/SQLite restriction is this sheet's proposed support boundary, not
an upstream or existing AO recovery claim.

### 2. Durable lineage and lifecycle

Reuse `core/state.js:46-73` and SQLite `db.transaction`, as used by
`core/repositories/lifecycle_repo.js:270`; no JSON files or new storage
engine. Add one versioned recovery table through the existing verified
migration machinery (`core/sqlite_migration_sets.js:26-70`). Keep frozen
historical migration files/digests unchanged. Define the immutable historical
root prefix `H` in its current order:
`001_initial`, `002_coordination_consumer`, `002_lifecycle`,
`003_coordination_ack_outbox`, `004_coordination_consumer_runtime_owner`.
Let `E` be the existing profile entry
`005_coordination_consumer_runtime_epoch`, and `R` the new
`005_request_context_lineage` entry at
`gateway/migrations/005_request_context_lineage.sql`, with its verified digest.
Append independently to each existing profile:

| Exported profile | Ordered sequence after A/0/05 |
|---|---|
| `GENERIC_APPLICATION_SQLITE` | `H`, then `R` |
| `WIRING_A_SQLITE` | `H`, then `R` |
| `WIRING_B_EPOCH_SQLITE` | `H`, then historical `E`, then `R` |

Do not insert `R` into the shared historical root prefix before WIRING-B's
already applied `E`, sort entries by filename, rewrite applied ledger rows,
or weaken exact-prefix/schema/digest validation. Preserve the ordered applied
prefix of every existing profile (`sqlite_migration_sets.js:154-174`), each
historical row's ID/rowid/applied timestamp, and existing cross-profile refusal
checks (`tests/gateway/coordination_consumer_epoch_migrations.test.js:345-420`).
Two entries with numeric prefix `005` have different full IDs; their explicit
profile order is binding. No new profile is introduced. PostgreSQL's adapter
has no transaction API (`core/postgres_db.js:6-24`); do not invent one here.

The recovery row is keyed by `traceId` and records schema version 1,
OS principal, machine digest, canonical state path, audience, original
context `expiresAt`, owner connection/process identity and an integer
revision. Its DB-backed payload records these exact bindings:

- Tasks: `taskId`, `repositoryId`, `canonicalRoot`, `targetAgent`,
  `targetRole`, canonical `targetAction`.
- Supervised sessions: `sessionId`, `taskId`, `tmuxTarget`, `targetAgent`,
  `targetRole`; each must reference a recorded task in the same trace.

The new migration also adds nullable `tasks.target_action`: existing task
rows stay explicitly legacy; new server-owned assignments persist their
resolved canonical action. The base task row lacks that field
(`core/repositories/task_repo.js:22`), so a recovered action must be compared
with this authoritative value rather than inferred from a role or defaulted
to `code.read`. A missing or mismatched action refuses recovery.

Create the owner row when a trace is created; merge task bindings on
`task.assign` and supervised session bindings on `agent.spawn`. Persist only
server-owned effective bindings and actual stored/returned session targets,
not caller-authored reconstruction. The existing task/session rows remain
authoritative: verify trace, task, repo, agent, role and tmux target against
them on recovery. Missing, legacy, malformed, unsupported-version or
inconsistent recovery metadata grants no authority. Headless `agent.delegate`
sessions, artifacts and approval authority are not restored by this payload.

Metadata writes merge against the latest row in a SQLite write transaction;
a stale snapshot must not overwrite a later task/session binding. Publish
success and update in-memory lineage only after the durable write commits.
A write failure is an error, not a successful durable binding. A crash between
an existing business-row write and the metadata write leaves an incomplete
record which recovery refuses, rather than inferring ownership from the DB.

Use the trace's original context expiry unchanged: `now >= expiresAt`
refuses recovery, and reattachment never renews it. Current-context expiry,
revocation, audience, capability and action-version checks also apply.
A taskless trace is not reattachable. For every persisted task, require its
registry ID and freshly verified canonical root to equal the current
context's binding **before any lineage is rebound**; additional unrelated
repositories in the current context do not grant access to missing bindings.
A mismatch in any task refuses the entire operation.

Only canonical orchestration states `active` and `paused` are eligible.
Remove the durable trace and its recovery children after successful
completion or confirmed cancellation, and remove its recovered memory
bindings; remove a session's recovery entry and memory binding after a
successful kill. Every subsequent protected call using recovered lineage must recheck
terminal state, expiry and durable owner so already hydrated maps cannot
resurrect closed resources. A terminal business row defeats residual
metadata even if cleanup was interrupted. Keep existing cancellation
semantics: `orchestration_service.js:83-90` requires a server-owned outcome;
this sheet must not turn that refusal into a successful cancellation. Test
cleanup against an actual canonical cancellation transition
(`core/lifecycle.js:58-59`) and test that a refused cancel does not erase it.

### 3. Explicit reattach and concurrency

Add canonical tool/action `orchestration.reattach` with strict input
`{ traceId: nonempty string }` and the normal orchestrator capability.
No identity, repository, connection, expiry or tmux target is caller-settable.
Never seed or claim recovery lineage on connect, discovery, a denied call,
or ordinary `orchestration.view { traceId }`.

A persisted trace must not be stolen from a still-live connection. Store
its Gateway owner's connection ID, PID, Linux process start token and kernel
boot ID (`/proc/sys/kernel/random/boot_id`). Reuse
`adapters/process_supervisor.js:402` for process identity
through the service/composition boundary; the kernel boot ID scopes PID/start
identity to one boot. An explicit release at shutdown follows context
revocation. After an abrupt stop, only positively established absence of
that process identity allows a new connection to claim it. A live owner or
unreadable/ambiguous liveness observation refuses; no timeout-based lease
stealing. A different start token at a reused PID or a changed verified boot
ID establishes that the recorded identity has ended; null from the existing
reader alone does not establish absence. Same-current-connection retries are
idempotent and revalidate state.

Use a SQLite immediate write transaction for read/validate/claim and revision
update; stage memory bindings until commit. Competing connections must have
one winner; the loser cannot acquire a trace, task or session. Serialize
same-trace recovery metadata/lifecycle changes and re-read authoritative rows
inside the transaction. No async transaction callback or lock spanning
provider work. The reattach transaction performs only bounded synchronous
local observations: exact-target `tmux has-session` via existing argv-based
`tmuxSync` (`adapters/tmux_client.js:28`), at most 1 second per probe and a
5-second overall probe budget. Exhausted budgets, command failures other than
confirmed absence, lock contention or ambiguous results deny with no partial
memory claim; bounds are fixed, not new configuration knobs.

For an authorized trace, restore matching task bindings and only sessions
whose authoritative status is `starting` or `running` and whose exact tmux
session still exists. Confirmed gone targets are reported and not hydrated;
never send input, start a child or kill a target as part of recovery. Return:

```text
{ traceId, reattachedTaskIds: string[], reattachedSessionIds: string[],
  skippedSessions: [{ sessionId, reason: "target_gone" | "session_closed" }] }
```

Sort ID arrays by ID, report each skipped session once, and expose no raw
paths, OS/machine/process identity, connection IDs or tmux output. A trace
with tasks but no surviving sessions can be reclaimed with an empty session
array and the corresponding skipped entries; it does not claim a live child.

### 4. Safe discovery and operator observability

`orchestration.view` accepts strict `{ traceId?: nonempty string }`.
With a trace ID it keeps its existing owned-trace response and authorization.
Without one it returns
`{ reattachableTraces: [{ traceId, status: "active" | "paused", expiresAt }], truncated: boolean }`.
Apply the same supported-identity, owner/repository, original-expiry,
lifecycle, non-taskless and prior-owner-liveness filters as reattach. Sort by
trace ID and emit at most 100 entries; `truncated` counts only otherwise
eligible entries. Discovery grants no ownership and needs no tmux probe;
live-target checks happen on explicit reattach. Foreign, incomplete, expired
and unsupported records leave no entries, counts or distinct error in the
response. An explicit saved trace ID remains usable beyond the discovery cap.

All authorization/recovery denials preserve the fixed
`REQUEST_CONTEXT_DENIED` public error envelope. In an ordinary denied
trace/session call, a persisted trace meeting the discovery filters may emit
operator-only `context.trace_reattachable`; it still grants no ownership.
Add a server-supplied private denial observer through the protected tool
wrapper (`tools/tool_helpers.js:158`, `:195`) before sanitization, wired by
`mcp_server.js`; its current escaped-exception logging path (`:189-203`)
does not observe normal caught denials. Emit only allowlisted reason/tool
metadata to stderr/audit; never raw args, roots, credentials, prompts, pane
content or foreign lineage. Observer failure cannot change the public result
or grant authority. Tests must capture an actual denial reaching this observer.

Append `orchestration.reattach` to the 33 existing catalog entries, preserving
their order (34 tools total). Update the action catalog, tool bindings, generated
`gateway/contracts/mcp-tools-v1.json` and `docs/mcp-tool-catalog.md` together;
use existing `catalogProjection`/`renderToolCatalogMarkdown` exports and
projection tests. Keep the public action catalog version 1; the operation is
an additive tool and the view input change preserves existing valid calls.
Document the local recovery sequence and unsupported-backend/identity limits
in `gateway/README.md`. Root reconciles shared contract/docs and the write
scope registry serially with A/0/02 and A/0/04; no functional dependency is added.

## Non-scope

- Changing `context.connection_mismatch` (`request_context.js:311`),
  auto-connecting traces, or reattaching across OS principals/machines/repos.
- PostgreSQL recovery parity, remote authentication, host integration,
  cross-machine state portability, or unverified identity fallbacks.
- Restoring headless sessions, artifact grants or approval grants;
  new cancellation/process supervision semantics or policy edits.
