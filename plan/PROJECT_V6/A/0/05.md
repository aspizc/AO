## Problem

The Gateway's request context keeps its lineage (traces, tasks, sessions) in
memory only. `createGatewayRequestContext` (`gateway/src/core/request_context.js:918`)
seeds no lineage, so `seedLineage` (`:146`) starts empty, and each MCP server
start draws a fresh `connectionId: crypto.randomUUID()`
(`gateway/src/mcp_server.js:244`). When the host (Claude Code) restarts, the
stdio server restarts with it: every earlier `traceId` fails `ownedTrace`
(`request_context.js:405-410`, `context.trace_denied`) and the client sees only
`REQUEST_CONTEXT_DENIED`. The tmux children keep running, unreachable through
`agent_ask`/`agent_view`/`agent_kill`. Field evidence: on 2026-10-07 an
orchestrator drove six live sessions through raw `tmux send-keys` and
`capture-pane` for the rest of the build because the Gateway refused all of
them.

## Scope

1. Persist the lineage the context needs to re-own a session (trace id,
   repository binding, task ids, session ids with their tmux target, agent,
   role, principal) in the Gateway's existing state directory, written when
   the binding is created and removed on `agent_kill`/`orchestration_complete`/
   `orchestration_cancel`. Reuse the existing store and atomic-write helpers;
   no new storage engine.
2. A new tool `orchestration_reattach { traceId }`: re-binds a persisted trace
   to the current connection only if (a) the caller's principal and
   repository binding equal the persisted ones, (b) the trace is not complete,
   cancelled or expired, and (c) each persisted tmux target still exists
   (`tmux has-session`); sessions whose target is gone are reported, not
   re-bound. Never automatic on connect.
3. `REQUEST_CONTEXT_DENIED` stays the only client-facing message for denials;
   the operator log keeps the reason code (`mcp_server.js:189-203`), now
   including `context.trace_reattachable` when a persisted trace exists, so
   the operator knows to call `orchestration_reattach`.
4. `orchestration_view` lists reattachable traces for the caller's principal.

## Non-scope

- Changing the connection-binding rule for live traces (`context.connection_mismatch`
  at `request_context.js:311` stays).
- Re-attaching across principals or repositories (refused, see the human gate).
- Headless `agent_delegate` runs (no live session to re-own).

## TDD RED

In `tests/gateway/` (reuse the request-context and session fixtures),
failing on current `HEAD`: `a trace created before a restart is reattachable
by the same principal and repository`; `reattach is refused for another
principal`; `reattach is refused for another repository binding`; `reattach
skips a session whose tmux target is gone and reports it`; `a completed or
cancelled trace is not reattachable`; `nothing is reattached without an
explicit call`; `agent_kill removes the persisted session`.

## TDD GREEN

Persist lineage at creation, add `orchestration_reattach` to the tool
catalog and contracts (`gateway/contracts/mcp-tools-v1.json`), seed the
re-bound lineage into the current context, and document the restart path in
`gateway/README.md`.
