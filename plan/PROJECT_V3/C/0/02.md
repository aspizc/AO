## Por que existe?

`gateway/src/core/postgres_db.js` materializa SQL en cliente (escapado
`pgLiteral`, :105-115) y lo ejecuta via `psql -c` (:72-76). El repo ya tiene
un primer contrato live opt-in en `tests/gateway/postgres_state.test.js`
(`AGENTS_TEST_DB=postgres` + `AGENTS_TEST_DB_URL`), pero la auditoria sigue
abierta porque falta endurecer esa ruta: nombre de gate consistente,
documentacion visible, comprobacion de entorno clara y casos adversariales de
escapado que un executor falso no detecta. `docker/docker-compose.yml` ya
provee Postgres 16 con healthcheck.

**Decision del owner (registrada en `plan/PROJECT_V3/README.md`):** la
migracion del executor `psql` a un driver `pg` con parametros bound queda
FUERA de V3. Esta tarea anade solo la cobertura real opt-in.

## Que hay que hacer?

Completar la suite opt-in de Postgres real: mantener los contratos de paridad
existentes, normalizar/documentar el gate (`AGENTS_PG_INTEGRATION=1` o
compatibilidad explicita con `AGENTS_TEST_DB=postgres`), y anadir casos
adversariales de escapado/parseo contra el Postgres del compose.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V3-C-0-2-postgres-integration-optin
```

### 2. Patron de gating

Replicar el patron de `tests/e2e/mcp_two_agent_real.test.js:20-25`
(`skipReason()`): la suite se skipea salvo que el gate opt-in este activo,
`psql` este disponible y el Postgres del compose responda (`pg_isready` o
query trivial). Skip con mensaje claro, nunca fallo por entorno ausente.

Compatibilidad requerida: si se cambia el gate historico
`AGENTS_TEST_DB=postgres`/`AGENTS_TEST_DB_URL`, dejar una ventana de
compatibilidad o actualizar todos los docs/tests que lo mencionan en el mismo
commit.

### 3. Suite

Opcion preferida: ampliar `tests/gateway/postgres_state.test.js` si el cambio
es pequeno; crear `tests/gateway/postgres_real_integration.test.js` solo si
los casos adversariales hacen ilegible la suite existente.

- Setup: URL default del compose
  `postgres://agents:agents@localhost:5432/agents`, override por env
  documentada, y limpieza idempotente. Si no se puede crear schema/database
  efimero con el executor actual, limpiar tablas en orden como hace la suite
  live existente y documentar el tradeoff.
- Reusar los contratos de paridad existentes: ejecutar contra
  `PostgresDatabase` real los mismos casos que el fake
  (insert/select/update/delete por cada repo,
  `changes` count, named vs positional params).
- Casos de escapado adversarial (el valor de la suite real): strings con
  `'`, `''`, backslashes, `:variable` estilo psql, saltos de linea, emoji,
  `NULL` vs `"null"`, numeros no finitos (debe lanzar, `pgLiteral:108-110`).
- Teardown: drop del schema efimero o limpieza idempotente de tablas.

### 4. Documentacion y gate

- `docs/v1-postgres-repository-tests.md`: seccion de como ejecutar la suite
  real (`docker compose -f docker/docker-compose.yml up -d postgres` +
  env opt-in documentada + `npm --prefix gateway test`).
- `scripts/ci.sh` NO la activa (opt-in local); el workflow de Actions
  tampoco.

### 5. Verificacion

Con compose arriba: suite verde. Sin compose: suite skipeada con mensaje.
Romper a proposito un caso de escapado (mutar `pgLiteral` localmente) y ver
la suite real fallar donde el fake no falla; revertir y anotar en la review.

## Errores comunes

- ❌ Migrar a driver `pg` "ya que estamos": fuera de V3 por decision del
  owner; si la suite real revela un bug de escapado, se abre hallazgo y se
  decide por separado.
- ❌ Apuntar a una database persistente del compose sin schema efimero: los
  runs deben ser idempotentes.
- ❌ Activar la suite en `ci.sh`/Actions: es opt-in local por diseno.
- ❌ Asumir credenciales: leerlas de `docker/docker-compose.yml` y permitir
  override por la env documentada (`AGENTS_TEST_DB_URL` o la que se normalice).
