## Por que existe?

`tests/gateway/approval_wait.test.js` usa `setTimeout` de 20-30ms para
inyectar la respuesta de aprobacion durante un `approval.wait`, y asercta
margenes de latencia estrechos (`<200ms`). En una maquina cargada (CI de
Actions de A/0/3 incluida) eso puede fallar de forma intermitente. Un gate
con flakes se ignora: el coste real es la perdida de confianza en el gate.

## Que hay que hacer?

Eliminar la dependencia de margenes absolutos: sincronizar por eventos donde
sea posible y, donde no, ampliar margenes con factor de holgura.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V3-D-0-2-approval-wait-timings
```

### 2. Revision de la suite

Leer la suite y clasificar cada assert temporal:

- **Orden/causalidad** (la respuesta llega DURANTE el wait): sustituible por
  sincronizacion — responder cuando el wait ya esta registrado (si el
  service expone estado consultable via `approvalRepo`/poll) en lugar de
  `setTimeout(20)`.
- **Cotas de duracion** (`<200ms`, expiracion de `maxWaitMs`): mantener la
  semantica pero con holguras x5-x10 (p.ej. wait cap de 40ms → asertar
  `< 1000ms`), o asertar solo el RESULTADO (decision devuelta/timeout) y la
  monotonia (`elapsed >= maxWaitMs` para el caso timeout) en vez de techos
  estrechos.

### 3. Regla general a aplicar

Ningun assert del gate depende de que algo ocurra en menos de 100ms. Los
`setTimeout` de inyeccion pueden quedarse (son disparadores, no asserts),
pero el assert posterior no debe asumir que el scheduler fue puntual.

### 4. Verificacion

```bash
for i in $(seq 1 20); do npm --prefix gateway test -- --test-name-pattern approval || break; done
```

20 ejecuciones consecutivas verdes (o el equivalente con la suite completa
si el filtro no aplica al runner actual).

## Detalle adicional de ejecucion

- Antes de cambiar tests, listar en la review los asserts temporales actuales
  y clasificarlos como causalidad, timeout o techo de latencia.
- No eliminar cobertura: cada assert retirado debe convertirse en assert de
  resultado, monotonia o estado observable.
- Si el runner Node no soporta `--test-name-pattern` con el script actual,
  usar el path directo de la suite (`node --test ...approval_wait.test.js`) y
  documentar el comando exacto de 20 runs.
- Mantener los valores de produccion (`AGENTS_APPROVAL_MAX_WAIT_MS`,
  `AGENTS_AGENT_TIMEOUT_MS`) intactos; la tarea toca tests, no servicio.
- Ningun nuevo margen debe ser menor de 100ms; preferir relaciones (`>= cap`)
  a techos absolutos.
