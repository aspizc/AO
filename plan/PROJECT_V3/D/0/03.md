## Por que existe?

Todo el historial vive bajo `## Unreleased` en el CHANGELOG (PROJECT_V0
A/0/0 hasta PROJECT_V1 E/0/1 mas todo V3): un lector no puede distinguir el
MVP2.0 cerrado del backlog. Ademas hay ~72 ramas `feature/*` mergeadas sin
podar. Cortar v0.1.0 marca formalmente el cierre y deja el repo legible.

## Que hay que hacer?

Seccion `## [0.1.0] - <fecha>` en el CHANGELOG, tag anotado `v0.1.0` en
`main`, y poda de ramas mergeadas en `develop`.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V3-D-0-3-release-0-1-0
```

### 2. CHANGELOG

- Mover el contenido de `## Unreleased` a `## [0.1.0] - <fecha>` con una
  cabecera-resumen de tres lineas: MVP2.0 (PROJECT_V0 A-Y), V1 experimental
  (A-E), V3 hardening (A-D), con enlaces a los checklists de aceptacion.
- Dejar `## Unreleased` vacio encima.
- Versionar los manifests: `gateway/package.json`, `cli/pyproject.toml` y
  `orchestrator-langgraph/pyproject.toml` ya estan en `0.1.0` — verificar y
  dejar constancia (no hay bump: esta ES la 0.1.0).

### 3. Tag (tras merge a develop → main segun flujo del repo)

```bash
git tag -a v0.1.0 -m "agents-orchestrator 0.1.0 — MVP2.0 + V3 hardening"
```

El push del tag y el merge a `main` requieren aprobacion del operador
(politica de ramas protegidas del propio proyecto: `git.push` a `main` es
`approval.git_push_protected`). Documentar el comando y dejar la ejecucion
final al operador humano.

### 4. Poda de ramas

```bash
git branch --merged develop | grep '^  feature/' > /tmp/merged_branches.txt
# revisar la lista A MANO antes de borrar; excluir la rama actual
xargs -n1 git branch -d < /tmp/merged_branches.txt
```

Solo `-d` (nunca `-D`): git se niega si una rama no esta realmente mergeada.
Listar las ramas NO mergeadas restantes en la review para decision del
operador (no se borran en esta tarea).

### 5. Verificacion

```bash
./scripts/ci.sh
git branch | wc -l       # reducido; reportar antes/despues
```

## Detalle adicional de ejecucion

- Esta tarea solo empieza cuando todas las reviews V3 previas tienen
  `reviewed_OK`; comprobar `plan/PROJECT_V3/reviews/*_reviewed_KO.md` y
  `*_to_review.md` pendientes antes de editar el CHANGELOG.
- Crear el tag anotado localmente solo cuando el commit de release este listo.
  El push del tag y cualquier merge/push a `main` quedan fuera sin aprobacion
  explicita del operador.
- Antes de podar ramas, guardar dos listas en la review: ramas mergeadas que
  se borran con `git branch -d`, y ramas no mergeadas que se dejan intactas.
- No usar `git branch -D`, `git push --delete` ni comandos remotos de poda en
  esta tarea.
- Si la release se prepara en `develop` y aun no se ha mergeado a `main`,
  documentar el comando exacto pendiente en la review en vez de simular que
  el tag ya esta publicado.

## Errores comunes

- ❌ `git branch -D` o borrar ramas no mergeadas: solo `-d` sobre la lista
  revisada.
- ❌ Pushear el tag o mergear a `main` sin aprobacion del operador.
- ❌ Reescribir entradas historicas del CHANGELOG al moverlas: se mueven tal
  cual, solo se anade la cabecera-resumen.
