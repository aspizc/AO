## Por que existe?

`tests/gateway/sanitizer.test.js` cubre reglas individuales y determinismo,
pero no la COMPOSICION: orden de aplicacion cuando varias reglas matchean el
mismo contenido, contenido con multiples tipos de secreto, reemplazos que
podrian re-matchear reglas posteriores, y el comportamiento con `appliesTo`
que no incluye el kind. El sanitizador (`gateway/src/core/sanitizer.js`, 32
lineas) aplica las reglas EN ORDEN DE ARRAY sobre el resultado acumulado:
ese contrato implicito debe quedar fijado, porque la sanitizacion es la
garantia central del flujo restricted.

## Que hay que hacer?

Ampliar la suite del sanitizador con casos de composicion, usando reglas de
fixture (no las de produccion) mas un caso con las reglas reales de
`policies/sanitization-rules.json`.

### 2. Casos (en `tests/gateway/sanitizer_composition.test.js`)

Con rulesets de fixture escritos a un tmpfile y `configureSanitizer`:

1. Dos reglas que matchean el mismo span → gana la primera del array; la
   segunda ve el contenido YA reemplazado (fijar con assert del orden en
   `appliedRuleIds`).
2. Reemplazo de la regla 1 que crea un match para la regla 2 → la regla 2 SI
   se aplica (cascada; documentar en el test que es el comportamiento
   actual).
3. Contenido con secreto + path + UUID simultaneos → los tres
   `appliedRuleIds` presentes, en orden de array.
4. Regla cuyo `appliesTo` no incluye el `kind` → no aplicada aunque matchee.
5. Replacement con `$&`/`$1` literales en el JSON de reglas → fijar el
   comportamiento actual de `String.replace` con backreferences (riesgo
   senalado en auditoria: un replacement con `$` se interpreta).
6. Contenido vacio y contenido sin matches → `appliedRuleIds` vacio,
   contenido intacto.
7. `sanitize` sin `configureSanitizer` previo → lanza "sanitizer not
   configured" (fail-closed).
8. Con las reglas REALES de `policies/sanitization-rules.json`: el fixture
   de secreto del E2E (`tests/e2e/mcp_two_agent_real.test.js:121-143` usa un
   token SECRET) queda eliminado.

## Detalle adicional de ejecucion

- Los rulesets sinteticos deben vivir en tmpfiles por test para no contaminar
  el estado global del sanitizador entre casos.
- Como `configureSanitizer` mantiene estado de modulo, importar con cache bust
  o reconfigurar explicitamente antes de cada caso que dependa de reglas.
- En el caso de cascada, asertar tanto `sanitized` como `appliedRuleIds` para
  demostrar orden real.
- En el caso `$&`/`$1`, escribir el resultado esperado del comportamiento
  actual de `String.replace`; no "arreglarlo" en esta tarea.
- El caso con reglas reales debe usar un secreto fixture controlado, no datos
  de workspace ni prompts reales.
