## Por que existe?

No existe `.github/workflows/`: todo el control de calidad es manual y local,
y nada impide que un commit roto llegue a `develop` o `main`. Decision del
owner (registrada en `plan/PROJECT_V3/README.md`): anadir un workflow minimo
que ejecute `scripts/ci.sh`. El gate local sigue siendo el autoritativo;
Actions es la red de seguridad remota. ADR-007 deja esa politica por escrito.

## Que hay que hacer?

Crear `.github/workflows/ci.yml` que ejecute `scripts/ci.sh` en push/PR a
`develop` y `main`, y `docs/adr/ADR-007-remote-ci-safety-net.md` con la
politica (gate local autoritativo + Actions como espejo).

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V3-A-0-3-github-actions
```

### 2. Workflow

`.github/workflows/ci.yml`, un solo job en `ubuntu-latest`:

1. checkout.
2. `actions/setup-node@v4` con node 20 (cache npm sobre
   `gateway/package-lock.json`).
3. `actions/setup-python@v5` con 3.11 (cache pip).
4. Instalar: `python -m venv .venv && . .venv/bin/activate`,
   `pip install -e "cli[dev]" -e orchestrator-langgraph`,
   `npm --prefix gateway ci`.
5. `./scripts/ci.sh` con el venv activado.

Consideraciones verificadas en el repo:

- `ci.sh` necesita `agent-run` en PATH (lo aporta el venv del paso 4).
- Los E2E son dry-run por defecto (no requieren tmux ni CLIs de agentes);
  `AGENTS_E2E_REAL` NO se setea en CI.
- Los tests Temporal/redis reales se auto-skipean sin sus env vars.
- `better-sqlite3` compila nativo: `npm ci` en ubuntu-latest es suficiente.

### 3. ADR-007

`docs/adr/ADR-007-remote-ci-safety-net.md` (formato de los ADR existentes:
Status/Context/Decision/Consequences): el gate autoritativo es
`scripts/ci.sh` local + flujo coder/reviewer; Actions ejecuta exactamente el
mismo script (sin logica propia en YAML) como deteccion remota; los caminos
reales (tmux, Codex/Claude/Gemini, Temporal, Postgres) quedan fuera de CI
remota por diseno.

### 4. Verificacion

Push de la rama y comprobar el run verde en Actions; abrir un PR draft y
verificar que el check aparece.

## Detalle adicional de ejecucion

- El workflow debe tener permisos minimos (`contents: read`) y no requerir
  secretos. Los caminos reales (`AGENTS_E2E_REAL`, Postgres, Temporal) no se
  activan en Actions.
- Usar `npm --prefix gateway ci`, no `npm install`, para respetar el lockfile
  Node.
- Si el entorno local no permite observar GitHub Actions, el `to_review`
  debe marcar la comprobacion remota como pendiente de operador y aun asi
  incluir verificacion estatica: workflow existe, triggers correctos y llamada
  unica a `./scripts/ci.sh`.
- ADR-007 debe enlazar a `scripts/ci.sh` como fuente de verdad y explicar que
  no hay logica de test duplicada en YAML.
- No anadir matriz de versiones: V3 fija Node 20 y Python 3.11, que son las
  versiones documentadas para el repo.

## Errores comunes

- ❌ Reimplementar los pasos del gate en YAML: el workflow llama a
  `scripts/ci.sh`, unica fuente de verdad.
- ❌ Setear `AGENTS_E2E_REAL=1` o instalar tmux/CLIs de agentes en CI.
- ❌ Olvidar el venv: `agent-run policy validate` falla sin
  `pip install -e cli`.
