## Por que existe?

`gateway/src/core/policy_engine.js` (289 lineas) es el nucleo de autorizacion
y NO tiene fichero de test propio: se cubre solo indirectamente via las 5
suites de aspecto (`tests/gateway/policy_*.test.js`) que llaman a
`evaluate()`. Los helpers con casuistica delicada no tienen tests directos:
`normalizePolicyPath` (:19-35), `pathMatchesExcludedPath` (:37-47),
`matchesProtectedBranch` (:120-125), `actionMatchesDeny` (:15-17) y el
comportamiento default-allow de `runPipeline` (:271). Un edge case erroneo
aqui autoriza en silencio. Ademas, B/0/2 (ADR de semantica de roles) necesita
esta base para medir el antes/despues.

## Que hay que hacer?

Crear `tests/gateway/policy_engine.test.js` con >= 15 casos que fijen el
comportamiento actual del motor, usando `explain()` (que ya expone el trace
por capa) y registries de fixture temporales. NO se modifica el motor: son
tests de caracterizacion.

### 3. Casos minimos (via `explain()` / `evaluate()`)

Paths y exclusiones (`pathMatchesExcludedPath`, `normalizePolicyPath`):

1. `path = "a/secrets/b"`, excludedPath `"secrets"` → DENY
   `classification.excluded_path` (semantica segmento-en-cualquier-posicion).
2. `path = "secrets"` exacto → DENY.
3. `path = "src/secrets-utils.js"` → ALLOW (no es segmento exacto).
4. `path = "../../etc/passwd"` → fijar el resultado actual de la
   normalizacion (el `pop()` sobre array vacio no lanza; documentar que
   resuelve a `"etc/passwd"`).
5. `path` con backslashes Windows (`"a\\secrets\\b"`) → mismo resultado que 1.
6. `path` con `"."` y `"//"` redundantes → normaliza igual.

Ramas protegidas (`matchesProtectedBranch`):

7. `targetBranch = "main"` con pattern `"main"` en `git.push` →
   REQUIRE_APPROVAL `approval.git_push_protected`.
8. Pattern `"release/*"` con branch `"release/1.2"` → REQUIRE_APPROVAL.
9. Pattern `"release/*"` con branch `"release"` (sin slash) → fijar
   comportamiento actual (el slice deja `"release/"`, no matchea).

Acciones y deny-list (`actionMatchesDeny`, default-allow):

10. Rol con `denyActions: ["code.write"]` y accion `"code.write.file"` →
    DENY por prefijo.
11. Accion desconocida `"foo.bar"` con agente/rol/repo validos → **ALLOW**
    (`reason: "all layers passed"`). Este test DOCUMENTA el default-allow
    actual; referenciar el hallazgo S2 en un comentario.
12. Agente desconocido → DENY `agent.unknown` (primera capa corta).
13. Repo desconocido → DENY `repo.unknown`.

Modelos y reasoning effort:

14. `agent.delegate` con `model` fuera del allowlist del agente → DENY
    `agent.model.allowed`.
15. `model` omitido con `defaultModel` valido → ALLOW con `model` efectivo
    resuelto en el resultado.
16. `reasoningEffort` invalido → DENY `agent.reasoning_effort.allowed`.

Orden y trace de capas (via `explain()`):

17. El trace contiene las 5 capas en orden
    `classification, model, role, approval, sanitization`.
18. Un DENY en `classification` corta el pipeline (capas posteriores no
    aparecen evaluadas con decision).

## Detalle adicional de ejecucion

- Mantener los helpers privados: cada caso debe observarlos por
  `evaluate()`/`explain()` y por los `ruleId` resultantes.
- El fixture temporal debe tener datos minimos pero completos: agente,
  repositorio, rol, ramas protegidas y reglas de sanitizacion aunque una
  prueba concreta no use todos los campos.
- El caso de path `../../etc/passwd` se fija mediante un `excludedPaths`
  adecuado y no mediante exportar `normalizePolicyPath`.
- El test de trace debe comprobar orden y corte: una denegacion temprana no
  debe aparentar que las capas posteriores permitieron la accion.
- Si alguna decision actual parece insegura, documentarla en el nombre del
  test o comentario breve y dejar el cambio de comportamiento para B/0/2.
