## Por que existe?

`gateway/src/config.js:55-57` traga cualquier excepcion al leer/crear
`secrets/message-access.key` y cae en silencio a un secreto por-proceso
(`PROCESS_MESSAGE_ACCESS_SECRET`). Consecuencia: los tokens de acceso a
mensajes dejan de verificar tras un reinicio y no hay NINGUNA pista en logs
de por que (p.ej. workspace de solo lectura, permisos). Fail-soft esta bien;
fail-soft mudo no.

## Que hay que hacer?

Emitir un warning estructurado JSON a stderr cuando se activa el fallback,
con el motivo del error y la ruta que fallo. Mantener el comportamiento
funcional identico.

## Plan de implementacion paso a paso

### 1. Branch

```bash
git checkout develop && git pull --ff-only || true
git checkout -b feature/V3-B-0-4-secret-fallback-warning
```

### 2. Cambio

En el `catch` de `loadOrCreateMessageAccessSecret` (config.js:55-57),
escribir a stderr una linea JSON con el mismo shape que `logErr` de
`mcp_server.js:17-27` (`ts`, `level: "warn"`, `component: "gateway"`, `msg`,
`error`, `secretPath`). `config.js` no importa el logger del server (evitarlo
para no crear dependencia circular config→server): replicar el formato con
un `process.stderr.write` local. Regla del repo: stdout es del protocolo
MCP; SOLO stderr.

Anadir el motivo: capturar `err` en el catch (hoy es `catch {}` sin binding).

### 3. Tests

`loadConfig` acepta `env` inyectable; el caso de fallo se fuerza con
`AGENTS_MESSAGE_ACCESS_SECRET_FILE` apuntando a una ruta que no pueda actuar
como fichero de secreto (preferente: `tmpfile/secret`, donde `tmpfile` es un
fichero regular; evita depender de permisos 0o000, que pueden comportarse
distinto segun usuario/plataforma). Test nuevo
`tests/gateway/config_secret_fallback.test.js`:

- Caso fallback: secreto devuelto tiene longitud valida, y stderr capturado
  contiene `"level":"warn"` y la ruta.
- Caso normal: ningun warning emitido.
- `AGENTS_MESSAGE_ACCESS_SECRET` en env: ni warning ni I/O.

## Detalle adicional de ejecucion

- Capturar `process.stderr.write` en el test y restaurarlo en `finally`.
- El warning debe ser una sola linea JSON parseable; asertar campos, no solo
  substring libre.
- El campo `error` debe usar `err.message` o `String(err)` y el campo de ruta
  debe ser la ruta fallida; nunca incluir el secreto ni su longitud exacta.
- El camino `AGENTS_MESSAGE_ACCESS_SECRET` debe retornar antes de calcular o
  tocar el fichero de fallback.
- Mantener stdout intacto: ningun test debe observar salida por stdout.
