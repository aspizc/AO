## ¿Por que existe?

V1 es hibrido: algunos flujos usan LangGraph y otros siguen con LLM. La seleccion debe ser explicita, auditable y vivir fuera del Gateway.

## ¿Que hay que hacer?

Crear `orchestrator_langgraph/selector.py` con seleccion por variable de entorno `AGENTS_ORCHESTRATOR_<FLOW>=langgraph|llm`.

El selector vive fuera del Gateway. No debe mutar tablas internas del Gateway ni
anadir campos al contrato MCP. Cuando LangGraph cree una orquestacion nueva,
puede usar `orchestration.create(callerAgent="langgraph", callerRole="orchestrator")`.
Si selecciona sobre una trace ya existente, debe devolver una decision local
auditable por tests/artifacts, no escribir metadata nueva en el Gateway.

## Plan de implementacion

1. Definir nombres canonicos de flows (`implement-test-review-push`, `plan-refine`).
2. Implementar resolucion de env vars con default conservador a `llm`.
3. Exponer una decision estructurada con `flow`, `selected`, `source` y `env_var`.
4. Tests para default, override valido y valor invalido.
5. Tests que verifiquen que la decision puede serializarse para audit/artifact
   sin requerir cambios en Gateway.

## Verificacion: Gateway contract inmutable

El selector vive fuera del Gateway. El Gateway no necesita saber si el caller es LLM o LangGraph.
