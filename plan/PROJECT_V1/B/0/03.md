## ¿Por que existe?

Los grafos de produccion deben atravesar las mismas puertas humanas que el camino LLM. En particular, `push` no puede saltarse `approval.request`/`approval.wait`.

## ¿Que hay que hacer?

Implementar `approval_node` reutilizable que llama `approval.request` y luego `approval.wait` con timeout configurable.

Este nodo no ejecuta `git push`. Solo abre y espera la aprobacion para una accion
como `git.push` o `git.push.protected`, usando la policy existente del Gateway.
El nodo posterior decide si puede continuar segun `status`.

## Plan de implementacion

1. Definir input minimo del nodo: `trace_id`, `task_id`, `action`, `reason`, `timeout_seconds` y `context`.
2. Llamar `approval.request` via `GatewayClient`.
3. Llamar `approval.wait` via `GatewayClient`.
4. Integrar el nodo antes de `push_node` en `implement-test-review-push`.
5. Testear auto-approve acotado via Gateway y caso timeout/pending bloqueante.

## Verificacion: Gateway contract inmutable

El grafo no implementa auto-approve. La policy de approvals sigue viviendo en el Gateway.

## Criterios de aceptacion

- [ ] `approval.request` y `approval.wait` se invocan desde LangGraph.
- [ ] Auto-approve acotado funciona solo si el Gateway lo concede.
- [ ] Un approval `pending`/timeout no se resuelve dentro del grafo.
- [ ] Sin campos de policy nuevos en el estado del grafo.
- [ ] El nodo no ejecuta `git push`; solo decide si el flujo puede avanzar.
