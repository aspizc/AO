## ¿Por que existe?

LangGraph debe llamar a las MCP tools del Gateway exactamente como lo haria un LLM: via protocolo MCP sobre stdio. Este modulo es el unico punto de contacto desde Python con el Gateway y evita que cada nodo reimplemente la conexion.

## ¿Que hay que hacer?

Crear `orchestrator_langgraph/client/gateway_client.py`: clase `GatewayClient` que levanta `agents-gateway` como subprocess stdio, establece sesion MCP y expone `call_tool(name, args) -> result`.

## Plan de implementacion paso a paso

1. Confirmar dep `mcp` en `pyproject.toml`.
2. Implementar `GatewayClient` como async context manager con `__aenter__`/`__aexit__`.
3. Usar MCP Python SDK para sesion stdio.
4. Exponer `call_tool(name: str, args: dict) -> dict`.
5. Inyectar `AGENTS_TRACE_ID` en el env del subprocess Gateway.
6. Test unitario con Gateway mockeado para serializacion/deserializacion.
7. Test de integracion opt-in (`AGENTS_INTEGRATION=1`) que llama `orchestration.ping` o smoke equivalente.

## Errores comunes

- Abrir socket TCP; el Gateway de V1 se consume por stdio.
- No propagar `traceId` al subprocess.
- Ocultar excepciones de protocolo MCP; el cliente debe fallar de forma visible.

## Verificacion: Gateway contract inmutable

El cliente consume tools existentes. No se anaden ni renombran tools para acomodar LangGraph.
