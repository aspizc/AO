## ¿Por que existe?

Las llamadas MCP deben ser reintentables sin duplicar efectos como spawn, review o push. La idempotencia vive en el borde activity/Gateway, no en el grafo.

## ¿Que hay que hacer?

Implementar activities (`delegate_activity`, `review_activity`, `push_activity`) que llaman `GatewayClient` con `activity_id` derivado de `(trace_id, node_name, attempt_number)`.

## Plan de implementacion

1. Definir contrato de input/output para activities.
2. Generar `activity_id` deterministico.
3. Propagar `trace_id` y `activity_id` al Gateway.
4. Probar reintentos con respuesta cacheada cuando aplique.
5. Fallar de forma visible ante errores MCP no recuperables.

## Verificacion: Gateway contract inmutable

No se crean tools nuevas; si el Gateway soporta idempotency keys, se usan como metadata/contexto sin cambiar nombres de tools.

## Criterios de aceptacion

- [ ] Activities llaman MCP via `GatewayClient`.
- [ ] `activity_id` deterministico probado.
- [ ] Reintentos no duplican efectos.
- [ ] Errores no recuperables no se ocultan.
