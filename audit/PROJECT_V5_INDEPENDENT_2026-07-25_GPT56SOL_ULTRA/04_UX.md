# Auditoría independiente de UX e interacción — agents-orchestrator V5

Model: gpt-5.6-sol

Reasoning: ultra

Execution profile: fast/priority

Snapshot: `develop` @ `d521afb12a6520b95f1a9fb172911b16ab77a1ff`, inspeccionado en `/tmp/agents-orchestrator-v5-audit.dx0UlX/worktree`.

Independence: revisión nueva e independiente; no se leyó ni utilizó ningún informe o artefacto de auditoría/revisión previo o de esta oleada. El análisis fue de solo lectura sobre el snapshot. Las únicas escrituras de ejecución fueron workspaces efímeros y autocontenidos de los smokes, eliminados al terminar; no se inició, detuvo ni contactó ningún MCP, Redis o Postgres compartido y no se usó red.

## Executive Summary

1. **Nota global de calidad UX: D**: el motor completa el flujo MVP2 en `dry-run`, pero una persona o un LLM que siga únicamente las interfaces publicadas no puede recorrer de forma fiable el flujo principal sin conocer el código o corregir instrucciones contradictorias.
2. **Accesibilidad estimada:** WCAG 2.2 AA y EAA son **no evaluables/no aplicables como declaración de conformidad**, porque el producto no expone GUI, DOM, rutas web ni aplicación móvil; la accesibilidad terminal es parcial y presenta dos barreras materiales, sin que constituyan por sí mismas fallos WCAG formales.
3. El mayor riesgo es la aprobación humana: la tabla que anuncia `APPROVAL_REQUIRED` no muestra `approvalId`, acción ni contexto, y `agent-run approve` decide inmediatamente sin una vista previa suficiente.
4. El segundo riesgo es la divergencia entre contrato e instrucciones: los prompts y runbooks ordenan invocar `policy.check`, `artifact.get.sanitized` y `artifact.put.review_notes`, pero ninguno de esos nombres existe entre las 32 tools MCP observadas y las llamadas fallan con `unknown tool`.
5. El tercer riesgo es un estado de sistema engañoso: se reprodujo una orquestación `completed` cuya única tarea seguía `pending`, y no existe una interfaz para cerrar tareas ni listar/recuperar sesiones.
6. También se observaron errores de dominio como `NOT_FOUND` y `TRACE_ACCESS_DENIED` dentro de respuestas MCP marcadas como éxito (`isError: false`), lo que debilita la recuperación automática y la confianza del operador.
7. Las tres oportunidades con mayor retorno son crear una superficie de decisión e inventario para el operador, derivar prompts/documentación/schemas de un contrato único y hacer que cierre, reanudación y errores reflejen el estado real.
8. Deben preservarse el transporte `stdio`, el modo local-first, el `dry-run`, las salidas JSON, los códigos de error accionables y la documentación de recuperación de coordinación; no hace falta construir una GUI para resolver los problemas prioritarios.

No se halló ninguna superficie gráfica oculta. La calificación y las recomendaciones se refieren a la experiencia real de operador/desarrollador: terminal, cliente MCP, prompts, configuraciones y runbooks.

### Plataformas, inputs y madurez

- Plataformas declaradas: Linux, macOS y WSL; Node 20+, Python 3.11+ y `tmux` para supervisión (`docs/operator-guide.md:7-13`).
- Inputs reales: teclado, argumentos de shell, JSON/JSON-RPC y lenguaje natural mediado por un LLM. Mouse, touch, orientación y hover no aplican.
- Viewports relevantes: anchura de terminal, no píxeles. Se probaron 100, 80, 40 y 20 columnas.
- Localización: toda la interacción de producto está esencialmente en inglés; no hay selector de locale ni contrato i18n. La mezcla puntual de terminología de versiones/proyecto pesa más que la traducción.
- Madurez: MVP técnico local-first para personas expertas. El flujo implementado es más maduro que su interfaz de activación y recuperación.
- Necesidades de accesibilidad previsibles: salida sin color, uso con lector de terminal, braille/voz sobre texto lineal, terminal estrecho, automatización sin TTY y carga cognitiva de IDs largos.

### Flujos clave

1. Activación: instalar → validar políticas → ejecutar gates/smokes → configurar host → cargar prompt → primera orquestación.
2. Core loop MVP2: crear → asignar coder → spawn/ask/view → compartir artefacto sanitizado → revisar → aprobar → cerrar → completar/verificar.
3. Error, aprobación y reanudación: detectar bloqueo → comprender contexto → decidir o corregir → recuperar estado/sesión → reintentar.
4. Coordinación V5: registrar → heartbeat/discover → send → receive → procesar → ACK → recuperar/unregister.

La mayor sorpresa es que los smokes ejecutables usan correctamente las tools reales, mientras que varios prompts y runbooks que deberían guiar al LLM nombran acciones de política o clases de artefacto como si fueran tools MCP distintas.

## UX Audit

### Resumen de severidades

| Severidad | Cantidad | Interpretación |
|---|---:|---|
| Critical | 0 | no se observó una exclusión sin workaround en toda circunstancia |
| High | 7 | bloquea el core loop, permite una decisión desinformada o comunica estado falso |
| Medium | 6 | añade error/retrabajo material, especialmente en activación y operación estrecha |
| Low | 1 | drift de microcopy/terminología sin bloqueo directo |

### Hallazgos High

#### UX-H1 — La interfaz de aprobación no permite identificar ni evaluar con seguridad la decisión

- **Encontrado (observado):** una entrada sintética completa `APPROVAL_REQUIRED` con `approvalId`, `action`, requester y context se renderizó solamente como timestamp, type, traceId y eventId. El renderer fija esas cuatro columnas (`cli/src/agents_cli/output.py:45-65`). La guía dice localizar el evento y ejecutar `agent-run approve <approvalId>` (`docs/operator-guide.md:170-180`), pero no explica cómo obtener el ID.
- **Contexto perdido (observado en código):** `approval.request` persiste `context` como payload, pero el evento manual de audit no lo incluye (`gateway/src/services/approval_service.js:51-71`). La CLI solo ofrece resolver, no listar/ver pendientes (`cli/src/agents_cli/main.py:203-247`).
- **Impacto:** el operador queda bloqueado o concede una acción sin saber repo, branch, objeto, diff ni razón. Es una vulneración de visibilidad, prevención de error y libertad/control de Nielsen en el punto más sensible del producto.
- **Severidad:** **High**. Hay workarounds parciales (`--json`, conversación del host, estado interno), pero ninguno forma una vista de decisión completa.

#### UX-H2 — Los prompts/runbooks publican tools que el Gateway no expone

- **Encontrado (observado):** `tools/list` devolvió 32 nombres y no incluyó `policy.check`, `artifact.get.sanitized` ni `artifact.put.review_notes`. Las tres llamadas se reprodujeron y las dos primeras familias de alias devolvieron JSON-RPC `-32603 unknown tool`.
- **Dónde:** el prompt genérico ordena `policy.check` (`prompts/orchestrator_system_prompt.md:11-20`, `prompts/orchestrator_system_prompt.md:69-79`); el prompt MVP2 ordena el alias de get y el alias de review notes (`prompts/orchestrator_mvp2_two_agent.md:33-46`); el planning addendum habla de `artifact.put.plan` y `artifact.put.review_notes` (`prompts/orchestrator_planning_loop.md:10-33`). Las tools reales son `artifact.put/get/list/share` (`gateway/src/tools/artifact.js:58-126`) y no se construye una tool MCP de política (`gateway/src/tools/index.js:28-37`).
- **Impacto:** un LLM obediente falla exactamente en el preflight y el handoff/review. La nomenclatura obliga a recordar que algunos puntos son `action` o `kind`, no nombres de tool.
- **Severidad:** **High** por bloquear pasos centrales y erosionar reconocimiento sobre recuerdo.

#### UX-H3 — La elegibilidad de Codex en repositorios restricted se contradice entre interfaces

- **Encontrado (observado):** `agent-run policy check --agent codex --role restricted-coder --action code.write --repo cvlib` y la variante `role=coder/action=code.read` devolvieron `ALLOW`. El registry da a Codex clasificación y rol restricted (`policies/agent-capabilities.json:49-96`) y los repos restricted permiten Codex (`policies/repositories.json:4-12`).
- **Dónde diverge:** el prompt MVP2 afirma dos veces que Codex está prohibido en restricted (`prompts/orchestrator_mvp2_two_agent.md:21-23`, `prompts/orchestrator_mvp2_two_agent.md:71-76`); `docs/policy-examples.md:8-10` y `docs/policy-examples.md:24-26` esperan deny; README y la guía del adapter afirman que sí está permitido (`README.md:117-119`; `docs/adapters/codex.md:68-70`).
- **Impacto:** unos operadores/LLM rechazarán trabajo válido y otros confiarán en una política distinta de la que creen haber cargado. El problema afecta consistencia, match con el modelo mental y seguridad percibida.
- **Severidad:** **High**. La policy runtime sigue siendo autoritativa, pero la experiencia publicada enseña dos políticas incompatibles.

#### UX-H4 — “Completed” no significa que el trabajo esté cerrado

- **Encontrado (observado):** después de `create → task.assign → orchestration.complete → orchestration.view`, el trace estaba `completed` y la tarea seguía `pending`. Solo se expone `task.assign`.
- **Dónde:** la tarea nace siempre `pending` (`gateway/src/services/task_service.js:81-104`); `buildTaskTools` no ofrece view/start/complete/cancel (`gateway/src/tools/task.js:4-25`); la transición de orquestación escribe cualquier status sin preflight de child work (`gateway/src/services/orchestration_service.js:58-72`).
- **Impacto:** métricas, audit y el LLM pueden anunciar éxito cuando hay trabajo abierto. El usuario no recibe prevención, confirmación ni lista de bloqueos antes de completar.
- **Severidad:** **High** por falsa visibilidad de estado y cierre no fiable.

#### UX-H5 — Varios fallos de dominio se presentan como éxito MCP

- **Encontrado (observado):** `artifact.get` de un ID inexistente, `session.attach_info` de una sesión inexistente y `message.list` con token incorrecto devolvieron body de error pero `isError: false`.
- **Dónde:** `defineTool` marca error solo para validación o excepción (`gateway/src/tools/tool_helpers.js:51-88`); algunos handlers retornan `{error: ...}` como valor normal (`gateway/src/tools/artifact.js:74-112`; `gateway/src/tools/message.js:46-98`; `gateway/src/tools/session.js:8-19`). El contrato reconoce expresamente esa dualidad (`docs/gateway-error-contract.md:21-28`).
- **Impacto:** hosts que usan la semántica MCP estándar para mostrar estado, detener cadenas o reintentar ven una llamada exitosa. El LLM debe inspeccionar cada body y recordar excepciones.
- **Severidad:** **High** porque puede convertir deny/not-found en continuación silenciosa.

#### UX-H6 — No hay inventario recuperable de sesiones persistentes

- **Encontrado (observado/inferido):** `orchestration.view` agrega session principal, tasks y artifacts, pero no child sessions (`gateway/src/services/orchestration_service.js:47-55`). `session.attach_info` y `agent.kill/view/ask` exigen un `sessionId` conocido; no existe `session.list` (`gateway/src/tools/session.js:5-42`; `gateway/src/tools/agent.js:28-76`).
- **Recovery real:** el runbook ofrece `tmux ls` y ejemplos manuales (`docs/mvp2-orchestrator-runbook.md:163-185`), pero no restablece la relación trace↔task↔session en la interfaz Gateway.
- **Impacto:** tras reinicio del host, truncamiento de contexto o transferencia de turno, un operador no puede reconocer qué sesiones siguen activas, adjuntarse con confianza ni cerrar huérfanas.
- **Severidad:** **High** para un producto que vende sesiones supervisadas persistentes.

#### UX-H7 — La guía de primer uso no completa la primera orquestación que promete

- **Encontrado (observado en el flujo publicado):** la guía se presenta como camino “from clone to a successful local dry-run” (`docs/operator-guide.md:1-5`), pero su coder hace `agent.spawn` sin el `agent.ask` que entrega el trabajo, y la secuencia no mata sesiones ni llama `orchestration.complete` (`docs/operator-guide.md:91-168`).
- **Contraste observado:** el smoke que sí funciona incluye `agent.ask`, `agent.view`, dos `agent.kill` y `orchestration.complete` (`scripts/smoke_mvp2.mjs:184-195`, `scripts/smoke_mvp2.mjs:253-277`).
- **Impacto:** una persona que copia el tutorial aprende una secuencia incompleta y no obtiene la confirmación de cierre.
- **Severidad:** **High** porque el onboarding debe permitir completar la tarea sin ayuda.

### Hallazgos Medium

#### UX-M1 — Los schemas MCP son estructurados, pero no autoexplicativos

- **Encontrado (observado):** el schema real aporta type, required, enum básico y `additionalProperties: false`, pero no descripciones de campo, ejemplos, `minimum`, `minLength`, límites de array ni varios enums semánticos. `metadata` aparece como `{}`; `participantType`, `classification`, `messageType`, `model` y `reasoningEffort` son strings genéricos.
- **Causa visible:** el conversor Zod→JSON Schema solo mapea unas pocas clases y descarta refinements/descriptions (`gateway/src/tools/tool_helpers.js:16-40`). El propio runbook reconoce que `body` no anuncia `maxLength` (`docs/coordination-bus.md:45-51`).
- **Impacto:** el host no puede prevenir input inválido, explicar unidades ni ofrecer choices; el LLM debe buscar un runbook largo y recordar valores.
- **Severidad:** **Medium**: el error posterior es detallado, pero el sistema no previene el error.

#### UX-M2 — Las acciones destructivas no tienen affordances de riesgo o idempotencia

- **Encontrado (observado):** `tools/list` publica solo name, description e input schema (`gateway/src/mcp_server.js:208-213`). `orchestration.cancel`, `orchestration.complete`, `agent.kill` y `approval.respond` no incluyen annotations de read-only/destructive/idempotent ni una descripción de irreversibilidad/precondiciones (`gateway/src/tools/orchestration.js:31-51`; `gateway/src/tools/agent.js:67-75`; `gateway/src/tools/approval.js:20-28`).
- **Impacto:** un host no dispone de metadatos para diferenciar lectura, mutación y acción sensible o presentar confirmación coherente. El coste de la acción queda escondido detrás de verbs igualmente planos.
- **Severidad:** **Medium**, mayor en `approval.respond` y menor en status mutables.

#### UX-M3 — El perfil “host-agnostic” depende silenciosamente del working directory

- **Encontrado (observado en config):** los tres perfiles usan `./gateway/src/mcp_server.js`, `./workspace` y `./policies` (`client-config/mcp.json.example:4-10`; `client-config/profiles/codex-coder-claude-reviewer/mcp.json:4-14`). El manual deja la adaptación concreta al operador (`client-config/README.md:46-51`).
- **Impacto inferido:** si el host inicia desde otro cwd, Node no encuentra el server o el Gateway carga/escribe rutas distintas. El error aparece antes de que las tools puedan ayudar.
- **Severidad:** **Medium**; el usuario experto puede convertir paths a absolutos, pero no se le da un check copiable.

#### UX-M4 — Las llamadas headless largas no comunican progreso ni cancelación

- **Encontrado (inferido desde código):** `agent.delegate` y `agent.ask` esperan el subprocess hasta un timeout por defecto de 600.000 ms (`gateway/src/config.js:153-160`; `gateway/src/services/agent_service.js:103-141`, `gateway/src/services/agent_service.js:184-201`). Sus descripciones no anuncian latencia ni mecanismo de cancelación/progress (`gateway/src/tools/agent.js:44-64`).
- **Impacto:** durante hasta diez minutos el host puede parecer congelado; un operador no sabe si hay progreso, si es seguro abandonar o cómo reanudar.
- **Severidad:** **Medium**. `agent.spawn` + `view` sí ofrece un patrón alternativo observable.

#### UX-M5 — La tabla audit no adapta prioridad de información al ancho

- **Encontrado (observado):** a 80 columnas se truncaron type y traceId largos; a 40, timestamp/type/trace/event quedaron casi solo como prefijos. No hay vista vertical/detail/pager. A 20 columnas el help raíz truncó ambos flags a `--…`.
- **Dónde:** columnas fijas Rich sin reglas de prioridad (`cli/src/agents_cli/output.py:45-65`); Typer usa tablas y `add_completion=False` (`cli/src/agents_cli/main.py:27-32`).
- **Impacto:** quien opera desde split terminal, SSH móvil o lector lineal pierde justo el identificador necesario para filtrar/actuar. `--json` conserva datos, pero cambia a una experiencia de máquina.
- **Severidad:** **Medium**; analogía, no fallo formal, con WCAG 2.2 SC 1.4.10 (Reflow) y 1.3.1 (Info and Relationships).

#### UX-M6 — La coordinación V5 no está en el prompt primario

- **Encontrado (observado):** README enumera siete tools y su propósito (`README.md:121-146`); la tool list las expone; el prompt que define lo que “you can use” termina en message/session y no menciona coordinación (`prompts/orchestrator_system_prompt.md:11-20`).
- **Impacto:** un LLM configurado según la guía no registra presence, no hace heartbeat y no consulta peers salvo que un humano añada manualmente el runbook V5.
- **Severidad:** **Medium** porque coordinación es opcional/aditiva, pero es la superficie distintiva de V5.

### Hallazgo Low

#### UX-L1 — La microcopy de versión mezcla V3, V4, MVP2 y V5

- **Encontrado:** README declara release v0.1.0 “closing MVP2.0 plus PROJECT_V3” (`README.md:7-13`); la CLI se presenta como “V4” (`cli/src/agents_cli/main.py:27-32`); el package Gateway también dice V4 (`gateway/package.json:2-8`); el mismo producto documenta la coordinación V5.
- **Impacto:** el operador no sabe si una instrucción/perfil está vigente o es histórica.
- **Severidad:** **Low** aislada, aunque amplifica el drift de contrato.

### Accesibilidad aplicable y limitaciones

**Declaración formal:** no es posible declarar “WCAG 2.2 AA compliant”, “partial” o “non-compliant” para el producto completo porque no hay contenido web renderizado bajo control del repositorio. EAA tampoco puede evaluarse sin una categoría de producto/servicio y una interfaz final al consumidor. Cualquier UI del host MCP debe auditarse por separado.

| Check aplicable | Resultado | Interpretación |
|---|---|---|
| Operación por teclado | pass inherente para CLI/MCP; `tmux` depende del terminal | no hay controles pointer-only |
| No depender solo del color | pass observado | `ALLOW`, `DENY`, `REQUIRE_APPROVAL`, `OK`, `CORRUPT` permanecen como texto |
| Preferencia sin color | pass observado | `NO_COLOR=1` eliminó secuencias ANSI |
| Orden de lectura | parcial | output lineal; tablas Unicode no transmiten relaciones semánticas como un DOM |
| Reflow terminal | barrera material | audit pierde contenido a 40 columnas; help pierde nombres a 20 |
| Alternativa estructurada | pass parcial | `--json` evita tablas, pero obliga a tooling y no resuelve context ausente |
| Nombres/labels | parcial | commands tienen help; propiedades MCP carecen de descripciones |
| Status announcements/ARIA/focus | N/A | no DOM ni eventos live |
| Contraste | no medible de forma estable | depende del tema del terminal; `NO_COLOR` reduce riesgo |
| Target size/touch/orientation/reduced motion | N/A | no touch ni motion |
| Screen reader real | no probado | requiere Orca/VoiceOver/NVDA y terminal/host objetivo |

Las dos barreras de accesibilidad terminal que deben priorizarse son: (1) pérdida de IDs/acciones a anchos razonables y (2) dependencia de tablas Unicode para relaciones que una salida vertical/plana expresaría mejor. Son analogías con SC 1.4.10 y 1.3.1, no claims de incumplimiento WCAG.

### Strengths to preserve

- El happy path MCP real pasa de punta a punta en `dry-run`; no es una maqueta documental.
- `policy validate` ofrece status, path y counts y usa exit codes diferenciados.
- `--json` es consistente y stdout/stderr están separados (`cli/src/agents_cli/output.py:13-25`).
- Las decisiones usan palabra, `ruleId` y reason; el color es redundante (`cli/src/agents_cli/output.py:68-78`).
- La validación MCP devuelve todos los campos faltantes con path/message/code, no solo el primero (`gateway/src/tools/tool_helpers.js:63-72`).
- `approval.request` es no bloqueante y `poll/wait` documentan timeout/pending (`gateway/src/tools/approval.js:7-45`), una buena base para no congelar el flujo.
- El smoke MVP2 termina con un resumen humano compacto de agentes, modelos, sesiones, artefactos, audit, modo y resultado.
- El runbook de coordinación distingue seguridad, lifecycle, idempotencia, semantic ACK/transport ACK, recuperación y acción por error con una precisión poco habitual.
- El estado disabled de coordinación falla de forma localizada y no elimina las tools legacy.
- El naming namespaced y la separación por dominios son coherentes en la tool list real.

## UX Strategy

### Temas y estado objetivo

| Tema estratégico | Problema raíz | Estado objetivo | Principio |
|---|---|---|---|
| 1. Contrato único y ejecutable | prompts, docs, policies y tool registry derivan por separado | toda instrucción invocable se valida contra `tools/list` y todo ejemplo de policy contra el registry cargado | “La documentación también compila” |
| 2. Decisiones humanas informadas | audit/approve separan ID, contexto y acción | el operador ve una lista redactada de pendientes, inspecciona contexto y confirma una decisión inequívoca | “Nada sensible se decide a ciegas” |
| 3. Estado honesto y recuperable | status de trace, tasks y sessions no convergen | overview por trace con tasks/sessions/artifacts/approvals; completar requiere cero trabajo abierto o una excepción explícita | “Completed significa completo” |
| 4. MCP autoexplicativo | schema escaso y señal de error dual | choices, unidades, límites, ejemplos, riesgo e idempotencia visibles antes de llamar; todo fallo usa una señal uniforme | “Prevenir antes que reparar” |
| 5. Activación reproducible | tutorial/config dependen de conocimiento/cwd | un único quickstart hermético, copiable y verificable desde checkout nuevo hasta cierre | “Primer éxito sin conocimiento tribal” |

### Qué no rediseñar

- **No construir una GUI/dashboard web ahora.** Una CLI de operador e interfaces MCP bien diseñadas resuelven los bloqueos con menos superficie y sin introducir auth, navegador, responsive o nuevas obligaciones EAA.
- **No sustituir `stdio` ni los namespaces actuales.** Son consistentes y el smoke demuestra que funcionan.
- **No ocultar `ruleId`, error codes ni JSON detrás de copy amigable.** Añadir contexto humano sin perder precisión máquina.
- **No simplificar la semántica at-least-once de coordinación.** La complejidad es real; debe mostrarse progresivamente, no maquillarse.
- **No exigir AAA ni polish visual a un MVP técnico.** Sí exigir que teclado/texto, error, decisión y recovery sean inequívocos.

### Señales medibles de éxito

1. Un operador nuevo completa checkout→dry-run→review→approval→close sin consultar código, con ≥90% de task success en una prueba de cinco participantes.
2. Cero nombres de tool en prompts/runbooks que falten en `tools/list`; cero ejemplos de allow/deny que contradigan el registry del perfil.
3. Cien por cien de fallos de tool tienen `isError: true`, code estable, mensaje redactado y next action; ningún `{error: ...}` viaja como éxito.
4. Un operador identifica acción, target, requester, trace y contexto seguro de una aprobación y decide en <60 s sin abrir JSON raw.
5. Cero traces `completed` con tasks `pending/running` o sessions activas, salvo override explícito y auditado.
6. Tras reiniciar el host, un operador encuentra, adjunta o cierra todas las sesiones activas de un trace en <30 s.
7. El help y el audit conservan nombre de acción e identificadores accionables a 40, 80 y 120 columnas mediante layout adaptativo; nunca hay document-level concept equivalente a overflow/truncación destructiva.
8. Las llamadas con latencia >2 s emiten progreso o devuelven una operación consultable/cancelable.
9. CLI plain/JSON y `NO_COLOR` siguen pasando; se añade un smoke manual con lector de pantalla sobre el terminal soportado.
10. Si en el futuro aparece UI web, la definición de done será WCAG 2.2 AA, cero overflow horizontal de documento a 320 CSS px, foco visible y estados anunciados; hoy esa gate no aplica.

6. **S / impacto medio:** reemplazar en profiles los paths relativos por placeholders absolutos explicados y añadir un preflight copiable.
7. **S / impacto bajo:** actualizar “V4”, “X/0/2”, “Z/0/3” y la declaración de release.

### Design sketches para los tres items principales

#### Sketch A — Aprobación informada (D1.2)

- **Antes:** el operador ve `APPROVAL_REQUIRED` sin ID/action, busca JSON o logs, copia un ID y ejecuta una mutación inmediata.
- **Después:** `agent-run approvals pending` presenta una fila/card por decisión: `approvalId · action · repo/branch/target redactado · requestedBy · trace · age`. `agent-run approvals show <id>` ofrece el contexto seguro y el estado actual. `approve` repite un resumen: “Grant git.push.protected on sample-apps/main requested by X?” y requiere confirmación en TTY; CI usa un flag inequívoco y JSON.
- **Gotchas:** no renderizar raw payload/secret; evitar que el preview quede obsoleto; hacer idempotente la repetición; permitir denial rápido; mantener salida plain para lector de pantalla.
- **Validación:** cinco operadores deben decidir tres escenarios en <60 s, identificar correctamente target/impact y no abrir raw JSON; revisión específica de redacción y prueba no-TTY.

#### Sketch B — Contrato invocable, no aliases imaginarios (D0.1 + D1.1 + D2.1)

- **Antes:** prompts mezclan tool names, policy actions y artifact kinds; el LLM descubre el fallo solo tras `unknown tool`.
- **Después:** un catálogo canónico declara `tool`, `purpose`, fields, values, risk y ejemplo. Prompts dicen: “call `artifact.put` with `kind: review_notes`”. Una gate carga `tools/list`, extrae referencias de prompts/runbooks y prueba cada ejemplo contra el schema/profile.
- **Gotchas:** algunas strings como `artifact.put.review_notes` son actions de policy legítimas, no tools; la gate debe distinguir contextos. Los modelos permitidos pueden ser profile-specific.
- **Validación:** replay del prompt en el harness MCP sin unknown tool; cero divergencias en CI; caída de `INVALID_INPUT`/policy retrials en benchmark.

#### Sketch C — Overview y cierre honesto (D1.4 + D1.5)

- **Antes:** `orchestration.view` omite sessions; `complete` cambia status aunque tasks sigan pending.
- **Después:** el overview devuelve un resumen compacto: orchestration status, tasks por status, sessions activas/cerradas, artifacts y approvals. `complete` hace preflight y, si hay bloqueos, devuelve una lista accionable: “task ts-… pending; session ag-… running — ask/view/kill or cancel task”. Tras restart, el host reconstruye el contexto desde ese overview.
- **Gotchas:** definir estados terminales y carreras entre complete/kill; no exponer sessions de otro trace; decidir si una task fallida bloquea o permite complete-with-failures.
- **Validación:** pruebas create→complete rechazado, happy path limpio, crash→resume y carrera; cero traces completed con child work activo en el fixture.

## Open Questions

1. ¿La persona primaria es el operador humano, el LLM orquestador o el integrador MCP? El orden de la información y los defaults cambian según esa prioridad.
2. ¿Cuál es la política canónica para Codex en repositorios `restricted` y qué combinación role/action debe ilustrarse?
3. ¿Qué significa exactamente el lifecycle de una task: `pending`, `running`, `completed`, `failed`, `cancelled`; quién puede transicionar y cuándo puede cerrarse el trace?
4. ¿Qué campos de approval context deben ser visibles, cuáles deben redactarse y qué acciones requieren confirmación interactiva adicional?
5. ¿Qué hosts MCP son oficialmente soportados y qué cwd usan al lanzar servers? ¿Se puede documentar uno como referencia sin abandonar el contrato host-agnostic?
6. ¿Qué ancho mínimo de terminal se soportará: 40, 60 u 80 columnas? ¿Se garantiza ASCII/plain mode?
7. ¿Qué lector de pantalla/terminal se usará para la gate manual: Orca en Linux, VoiceOver en macOS u otro?
8. ¿Coordinación V5 debe formar parte del prompt base o de un addendum opt-in para no gastar contexto cuando Redis está deshabilitado?

10. ¿Qué browsers/dispositivos/locales serían soportados por una futura UI? Hoy son N/A; terminales declarados y lenguaje inglés deben documentarse explícitamente.
11. ¿Quién posee el contrato transversal tools↔policy↔docs↔prompts y puede bloquear un release cuando diverge?
12. ¿Se conserva el comportamiento de exit 1 para `require_approval` y `allow_with_sanitization` en `policy check`, o se documenta/separa de deny para consumidores shell?
